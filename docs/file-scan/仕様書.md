# file-scan 仕様書

[機能別ドキュメント一覧](../README.md)

指定フォルダの業務文書を収集し、原本を固定してから、本文・構造・位置を検索に使える単位で PostgreSQL に下書き登録する。ベクトル生成は別コマンドで実行する。検索への公開は管理者が業務リリースを指定して実行する。

[機能説明資料](機能説明資料.md) · [本番導入仕様](本番導入仕様.md) · [C++／Qt ソース取込の仕様](../cpp-scan/仕様書.md) · [検索 API の仕様](../file-search/仕様書.md)

## 1. 入力と CLI

| コマンド | 入力・処理 | 主な結果 |
| --- | --- | --- |
| `file-scan scan --config PATH` | 設定した収集元を列挙し、対象・除外・列挙エラーを分類 | `scan-*.json`。原本のコピーと DB 接続は行わない |
| `file-scan init-db --config PATH` | 取込スキーマの新規作成、または管理版 v1／v2 から v3 への非破壊更新 | `winnap.schema_migrations` に版 3。既存 `public` 配置は専用の移行手順を使う |
| `file-scan ingest --config PATH` | 列挙、原本固定、構造抽出、分割、文書単位で DB 登録 | 下書き世代、`ingest-*.json`、世代ごとのレビュー資料 |
| `file-scan ingest --config PATH --retry-partial` | 同一原本・同一設定でも部分抽出になった対象を再処理 | 再処理した箇所では抽出キャッシュを使わず、正常世代は再利用する |
| `file-scan embed --config PATH` | 有効時、現在の処理済み世代から未登録の検索用テキストをベクトル化 | `chunk_embeddings`、`embedding_cache`、`embed-*.json` |
| `file-scan status --config PATH` | ナレッジの現在状態、履歴、Embedding の準備件数を読む | JSON を標準出力へ表示 |

終了コードは `0` が正常または Embedding 無効、`1` が設定・DB・排他等の実行全体の失敗、`2` が列挙エラー・部分抽出・個別失敗・書き出し失敗等を含む完了、`130` がキーボードによる中断。コマンド引数の誤りでは argparse も `2` を返す。

### 収集元

`sources[].source_id` と収集元からの相対パスから文書 ID を作る。原本の版にはバイト列の SHA-256 を使う。同じ場所の内容変更は同一文書の新版、名称やパスの変更は別の文書になる。適用先の `knowledge_id` には固定の `system_id` と `environment` を対応付ける。

- 対象は既定で DOCX、XLSX、XLSM、PDF、TXT、MD。`.markdown` は明示設定で追加できる。`include_extensions` はこれらの部分集合を受け付ける。DOC・XLS・PPT/PPTX、単独画像、ソースコード、SQL、JSON、YAML、CSV、LOG は原本の対象外。
- `recursive: true` で配下まで走査する。`exclude_directories` は収集元相対のパス、`exclude_directory_names` は階層を問わない大文字小文字を区別しない名前の完全一致、`exclude_filenames` はファイル名に対する大文字小文字を区別しない glob。ディレクトリ除外は配下を探索せず、フォルダ単位で記録する。
- シンボリックリンク・ジャンクションは追跡しない。`include_hidden: false` が既定で、ドット名と Windows の隠し属性を持つファイル・ディレクトリを除外する。Excel 内部への適用は次節を参照。
- `storage_dir`・`report_dir` と各収集元の重複を避ける。YAML の相対パスは設定ファイルの位置を基準とする。Linux では SMB をマウントしてローカルパスを指定する。
- 既定のファイル上限は 100 MiB。収集中の変更を読込前後の属性・サイズで検査し、変更を検出した場合は `copy_retries` の範囲で再試行する（既定 2 回）。同一原本も通常は全バイトのハッシュを照合し、保管済み実体を検査する。内容が一致すれば一時ファイルの書込を省く。保管原本の不足は取得をやり直し、破損は失敗として記録する。

## 2. 形式別の抽出と位置

| 形式 | 抽出内容 | 原本位置・制約 |
| --- | --- | --- |
| TXT／Markdown | UTF-8（BOM 対応）または CP932 の段落。Markdown の ATX 見出しを構造化 | 行範囲。装飾の再現は対象外 |
| XLSX／XLSM | openpyxl と OOXML でシート、行、セル値、結合、数式、保存済み計算結果、貼付画像を抽出 | シート名・セル範囲・描画アンカー。数式は実行せず、保存済み結果の欠落を記録 |
| DOCX | OOXML の本文順に段落と表を読み、見出しスタイル・番号・目次参照・画像を保持 | 本文要素・段落・行などの構造上の位置。Word の表示ページ組版は再現しない |
| PDF（既定 Docling） | 文字層、レイアウト、見出し、表、図、日本語 OCR | 1 起点のページ番号と bbox 等。項目の座標系を位置情報に記録。複雑な段組み、表、縦書き・ルビは原本照合が必要 |
| PDF（`native`） | pypdf で文字層から抽出 | 構造復元と OCR は対象外。Docling 失敗時の自動フォールバックは行わない |

Excel ではシートの状態を棚卸しし、`include_hidden: false` の場合は非表示・veryHidden シートの本文に加えて、OOXML の `xdr:cNvPr` が `hidden="1"` または `hidden="true"` の描画を取り込みから外す。非表示グループの配下の画像も対象外になる。Office のプレビュー PDF を使う場合、該当描画を除いた一時コピーを LibreOffice に渡す。保存済み原本はそのまま保持する。Office パッケージには展開サイズ・XML サイズ・パーツ数・シート処理セル数の上限がある。

### PDF の日本語 OCR

Docling 2.140.0、RapidOCR 3.9.1、ONNX Runtime 1.24.1 CPU の固定構成で処理する。検出・方向分類・認識の ONNX 3 点と Docling のレイアウト／表モデルは lock のファイル一覧・サイズ・SHA-256 と照合する。OCR の言語は `iso:ja`、モデルは `small`、CPU 2 スレッド、採用スコア 0.5。モデル取得は事前準備で行う。

| `pdf_ocr` | 動作 |
| --- | --- |
| `enabled` | 既定 `true`。`false` では OCR 用モデルを読み込まない |
| `mode` | 既定 `auto` は文字層と必要な画像領域を使う。`full_page` は全ページを OCR し、既存文字セルを置き換える |
| `scale` | 基準 72 dpi に対する倍率。既定 3.0（216 dpi）、1～4 |
| `timeout_seconds` | OCR 有効時の Docling PDF 1 文書の解析期限。既定 1800 秒 |

原画像が 1 点でページ面積の 95% 以上を覆い、そのページで OCR セルと検索本文が得られた場合は背景扱い（`ocr_background`）とし、画像の解析待ちから外す。画像実体とページ参照は保持する。部分的な図は別に解析待ちになる。文字が取れないページは `pdf_page_without_text_after_ocr`、文書全体に抽出文字がない場合は `no_extractable_text` 等を確認する。レビュー用の `ocr_pages`、`ocr_text_cells`、`ocr_confidence_mean`、`ocr_background_pages` は処理結果であり、正解率の測定値ではない。OCR はローカルで実行し、ページ単位の途中保存・失敗ページだけの再開は提供しない。

### 画像の説明

`image_analysis.enabled` は既定で無効。有効にした PDF、XLSX／XLSM、DOCX では、抽出済みの図領域や埋込画像を OpenAI Responses API に送り、可視文字・説明・判読不能箇所を分けて保存する。既定モデルは `gpt-5.4-mini-2026-03-17`、1 文書の異なる画像は既定 20 点、1 回の期限は既定 60 秒。画像を PNG に整えて指示とともに送り、`store: false` を指定する。同一画像の認識は文書内で再利用する。

Office の図形を使う場合は `render_office: true` と実行ユーザーの PATH 上の `soffice` が必要。LibreOffice の一時プロファイルを使い、マクロや外部更新の設定を制限する。外部参照・埋込アプリ等を含む一部の文書はプレビュー生成を拒否する。プレビュー PDF から検出した領域には、プレビューのページ番号・座標系を付ける。印刷範囲やフォントで画像の見え方は変わり、切出しに周辺文字が含まれることがある。

OCR 本文・埋込原画像は原本由来の `source`、API が作った `image_description` は `derived` として区別する。認識待ち・タイムアウト・判読不能・上限などは品質情報に残す。画像説明を検索へ出すには原図と照合し、検索側の公開コマンドで `--include-image-descriptions` を指定する。部分完了の公開には `--allow-partial` も必要。

## 3. 分割、保存、再利用

### チャンクと根拠位置

ブロックを文書構造に沿って分割する。`content_text` は根拠本文、`search_text` は資料名・見出し・表の列見出し等の文脈と本文を含む検索入力。原文との範囲には Unicode コードポイントを使い、保存前に原文との一致を検査する。

- `chunk_max_characters` は本文の既定 1800 文字、`chunk_max_tokens` は検索入力の既定 8191 トークン、`chunk_context_max_tokens` は文脈の既定 1024（実効上限は全体予算の半分以下）。トークン数は `cl100k_base` で測り、`chunks.token_count` に記録する。
- 表は行境界を優先し、後続チャンクの検索入力にも列見出しを引き継ぐ。上限を超える行は原文範囲を残して分割し `table_row_split`、文脈を縮めた場合は `search_context_truncated` を付ける。
- `chunk_blocks` からブロックのページ、シート、セル、行などへ戻れる。レビューで原本・抽出結果・チャンクを照合できる。

### 保存先と取込用テーブル

`storage_dir` に原本・画像を内容ハッシュで保管する。DB は実体 ID・相対保管キー・位置・本文等を持つ。初回登録時の絶対保管先を `ingestion_settings` に固定する。保管先を移す際は DB 設定と実体を一緒に移行する。

PostgreSQL の取込表は `winnap` にあり、`public` の pgvector 型・演算子を使う。物理列・制約・索引は [配布 SQL](../../sql/postgresql/schema-v3.sql) を参照する。検索側の `winnap.search_*` は別の管理版を持つ。

| 用途 | 取込スキーマ v3 のテーブル |
| --- | --- |
| 初期化・設定 | `schema_migrations`、`ingestion_settings` |
| 収集範囲・原本 | `knowledge_bases`、`knowledge_documents`、`documents`、`document_versions`、`artifact_assets` |
| 現在選択・変換 | `conversion_profiles`、`extraction_generations`、`selected_generations`、`extraction_cache` |
| 構造・位置・派生 | `blocks`、`chunks`、`chunk_blocks`、`asset_occurrences`、`artifact_relations` |
| ベクトル | `embedding_profiles`、`chunk_embeddings`、`embedding_cache` |
| 実行管理 | `index_jobs` |

`report_dir` に `scan-*.json`、`ingest-*.json`、`embed-*.json`、`generations/<世代ハッシュ>/manifest.json`・`document.json`・`chunks.jsonl`・`review.md` を出力する。世代ファイルは DB の確定結果から再出力できる。出力先の書込失敗は `export_write_failed` として扱い、確定済み DB データは保持する。

### 再実行の単位

| 段階 | 再利用キーと条件 |
| --- | --- |
| 抽出 | 原本の SHA-256 と形式別 `extraction_revision`。パーサー・依存・抽出条件・PDF 固定モデル等が変わると再抽出。キャッシュと画像実体の整合を検証する |
| 分割・世代 | 文書 ID、原本版、`conversion_revision`。分割条件だけを変えた場合は抽出キャッシュから分割する。同一の成功世代、または再処理指定のない部分世代は実体を検査して再利用する |
| ベクトル | `embedding_profile_id` と実際に送る `search_text` のハッシュ。モデル・次元・入力版・文面が同じ場合は別世代でも既存ベクトルを再利用する |

DB 記録上の作成日時から現在世代を推測しない。`selected_generations` が現在の候補を決める。過去の原本版・世代は履歴として保持する。

## 4. 収集状態と検索への引き渡し

| 検知した状況 | DB と検索への反映 |
| --- | --- |
| 既存文書を再走査中 | 前回の `scan_status`、所属の収集状態、選択世代を保つ。DB へ新しい事実が確定するまでは現在の公開結果を維持できる |
| 新規発見・除外解除 | ナレッジ所属を追加または復帰し、収集待ちから原本・世代の登録へ進む |
| 列挙不完了の収集元で既存文書が見つからない | 該当ナレッジの所属を `scan_incomplete` の失敗にする。原本の共有状態は書き換えず、別ナレッジへ収集障害を波及させない |
| 除外設定に該当、または収集元を設定から外した | 所属を `included=false`・`excluded` とする。履歴は残す |
| 正常に列挙した収集元から文書が消えた | 原本を論理削除し、該当文書を含むナレッジのカタログ版を進める |
| 原本・選択世代・処理状態が変わった | 影響するナレッジの `catalog_revision` を進める。同じ文書を収める別ナレッジには原本の変更を、同じ変換世代を選択する別ナレッジにはペイロードの確定を反映する |

検索の `current` モードでは、公開コピーの原本版・選択世代・変換設定・世代更新時点が現在と一致する必要がある。取込で新版を選択・確定しても自動で公開は更新されない。取込状態と公開の採用条件は [検索 API の仕様](../file-search/仕様書.md) を参照する。

### 排他とジョブ期限

- `ingest` と `embed` は同一 DB のバッチ排他を使用する。中断したジョブは次回、排他取得後に `interrupted_previous_run` の失敗として回収し、別試行を作る。時間のかかるコピー・解析・API 通信のあいだに本文登録のトランザクションは開かない。
- 子プロセスへ API キー・DB 接続を渡さない。解析期限は OCR 有効の Docling PDF なら `pdf_ocr.timeout_seconds`、その他は `parse_timeout_seconds`（既定 120 秒）。spawn ワーカーは既定 1、設定可能数は 1～4。文書処理は順次行う。既定 100 回の処理、または処理後ピーク 1536 MiB でワーカーを交換する。ピーク判定は文書途中の強制上限ではない。
- 変換ジョブの占有期限は実際の解析期限に 300 秒を加え、画像認識の対象なら最大画像数×API 期限、さらに Office プレビューを行う設定なら描画 1 回分の期限も加算する。長時間の棚卸しは排他中に自分のジョブを更新して確定する。
- 変換本文・チャンク・抽出キャッシュは、有効なジョブを確定する同じトランザクションで保存する。期限切れの成功は拒否し、本人がまだ占有する期限切れ試行は失敗として記録して後続文書の処理を続ける。

### Embedding と状況確認

既定では無効。OpenAI Embeddings API の既定は `text-embedding-3-small`、1536 次元。対象は現在選択済みの成功・部分世代に紐づく未処理の `search_text`。プロファイルと入力ハッシュが一致する場合は再送しない。送信前のトークン上限と応答の件数・次元・数値を検査し、確定したバッチは後続で失敗しても残す。

DB 読込ページは既定 128 件・上限 1000 件、API 1 要求は既定 16 件・上限 32 件と、既定合計 262112・上限 300000 トークンの両方で制限する。1 入力の既定上限は 8191。レポートの `embedded`、`api_inputs`、`reused`、`unchanged`、`failed`、`unready_documents` を区別する。

`status` の `documents` は現在の所属件数。`generations` には `succeeded`、`partial`、`failed`、`pending`、`unavailable`、`stale`、`config_mismatch` の現在状態を集計する。`historical_generations` は除外分も含む処理履歴。`embeddings` はプロファイル別に `ready`／`pending`／`total` を表示する。検索公開の確認には検索側の状態も使う。
