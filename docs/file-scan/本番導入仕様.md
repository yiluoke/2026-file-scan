# file-scan 本番導入仕様

[機能別ドキュメント一覧](../README.md)

Windows ホスト上の Ubuntu 26.04 LTS VM に file-scan を導入する。アプリ、PostgreSQL、原本の保管先とモデルは Ubuntu 内に置く。共有フォルダは原本の読込に使う。この手順の Ubuntu VM、社内共有、実 API の受入結果は導入時に記録する。

[取込の仕様書](仕様書.md) · [機能説明資料](機能説明資料.md) · [C++／Qt ソース取込の本番導入](../cpp-scan/本番導入仕様.md) · [検索 API の本番導入](../file-search/本番導入仕様.md)

**手順へのリンク**　[Ubuntu](#ubuntu) ／ [Python](#python) ／ [DB](#database) ／ [設定とモデル](#configuration) ／ [共有フォルダ](#smb) ／ [受入確認](#acceptance) ／ [運用](#operation) ／ [復旧と移行](#recovery) ／ [閉域導入](#offline)

## 1. 構成と担当

| 項目 | 本環境での配置・方針 |
| --- | --- |
| Windows | 仮想マシンのホスト。仮想化ソフトの種類は未指定 |
| Ubuntu | 26.04 LTS。`uname -m`でCPUアーキテクチャを確認する |
| Python | Ubuntu標準の3.14系を使用。確認版3.14.4。標準版から仮想環境を作成する |
| DB | Ubuntu内のPostgreSQL 18＋pgvector 0.8.6。検索APIを使う場合はPGroongaも必須 |
| アプリ | `/opt/file-scan/`へソース一式、同ディレクトリの`.venv`へPython依存を導入する例 |
| アプリ設定・ソース | `/opt/file-scan/config.local.yaml`・`.env`。処理は`/opt/file-scan/src/file_scan/`と`/opt/file-scan/src/search/` |
| 原本・モデル・レポート | `/var/lib/file-scan/`配下。Ubuntu側のローカルディスクを使う |
| トークナイザー | `/var/cache/file-scan/tiktoken/` |
| 取込元 | SMB共有ならUbuntuへマウントし、`/mnt/file-server/department`等を指定する |

Windows／VM 管理者は VM の自動起動、ディスク容量、時刻同期、ネットワークを担当する。DB 管理者は拡張、DB と権限、整合したバックアップを管理する。取込担当者は収集範囲・抽出結果・エラーを確認し、公開担当者は根拠と公開対象を確認する。外部 API を使う場合は送信範囲・接続先・認証情報を導入先の管理者が管理する。

Ubuntu 26.04 の標準 Python は 3.14 系。リポジトリの検証基準は Python 3.14.4 と [固定依存](../../requirements/ubuntu-26.04.lock)。[依存の版照合用データ](../../requirements/ubuntu-26.04-baseline.json)と VM の実パッチ版を確認する。

従来の構築資料で確認した Ubuntu 26.04 の `postgresql-18-pgvector` は 0.8.1-2。本手順はリポジトリの検証基準に揃えて v0.8.6 の公式ソースを使う。VM での候補版は `apt-cache policy` で記録する。[Ubuntu の配布情報](https://packages.ubuntu.com/source/resolute/pgvector)

DBのデータ領域・実体保管先・キャッシュはUbuntuのローカルファイルシステムへ置く。Windows／NASの共有は取り込み元として使用する。同梱`compose.yaml`は開発用のため、この本番例はUbuntuへのネイティブ導入で記載する。

## 2. Ubuntu と実行ユーザー

管理者権限で実行する。以下のユーザー・ディレクトリ作成は新規の場合だけ行う。

```sh
cat /etc/os-release
uname -m
sudo apt update
sudo apt install -y ca-certificates curl git build-essential pkg-config software-properties-common cifs-utils python3 python3-venv libgl1 libglib2.0-0t64
sudo add-apt-repository -y universe
sudo apt update
apt-cache policy postgresql-18 postgresql-18-pgvector libgroonga-dev
sudo apt install -y postgresql-18 postgresql-client-18 postgresql-server-dev-18
sudo adduser --system --group --home /var/lib/file-scan file-scan
sudo install -d -o root -g root -m 0755 /opt/file-scan
sudo install -d -o file-scan -g file-scan /var/lib/file-scan/storage /var/lib/file-scan/reports /var/lib/file-scan/models
sudo install -d -o file-scan -g file-scan /var/cache/file-scan/tiktoken
sudo systemctl enable --now postgresql
pg_lsclusters
```

配布ソース一式を管理者が`/opt/file-scan/`へ直接配置し、配置先とソースはroot所有で実行ユーザーが読み取れるようにする。既存環境が`file-scan`所有の場合は処理を停止し、設定を保護してからプロジェクトのディレクトリと配布ソースの所有者・書込権限を見直す。移設元の`.venv`やDBデータ領域はコピーしない。実行ユーザーには共有の読込権限と`/var/lib/file-scan/`・`/var/cache/file-scan/`の必要な書込権限を与える。

## 3. Python と固定依存

新規導入時はsudoを使える一般ユーザーが、書き込み可能な一時ディレクトリで配布ソースのビルドを行う。仮想環境は最終パスに作成し、検査後にroot所有へ戻す。稼働中の仮想環境は上書きしない。

```sh
(
  set -eu
  umask 022
  build_dir="$(mktemp -d)"
  trap 'rm -rf -- "$build_dir"' EXIT
  test ! -e /opt/file-scan/.venv
  sudo install -d -o "$(id -u)" -g "$(id -g)" -m 0755 /opt/file-scan/.venv
  cp -R /opt/file-scan/{pyproject.toml,README.md,requirements,scripts,src} "$build_dir/"
  chmod -R u+w "$build_dir"
  cd "$build_dir"
  python3.14 --version
  python3.14 -m venv /opt/file-scan/.venv
  /opt/file-scan/.venv/bin/python -m pip install -r requirements/ubuntu-26.04.lock
  /opt/file-scan/.venv/bin/python -m pip install --no-deps --no-build-isolation '.[dev,search]'
  /opt/file-scan/.venv/bin/python scripts/check_python_environment.py
  /opt/file-scan/.venv/bin/python -m pip check
  /opt/file-scan/.venv/bin/file-scan --version
  /opt/file-scan/.venv/bin/file-search --help
  sudo chown -hR root:root /opt/file-scan/.venv
)
```

確認基準はPython 3.14.4。Ubuntuの保守更新でパッチ版が進んだ場合は、版の対応表とテスト結果も更新する。lockはLinuxのCPU用PyTorchを公式配布元から取得する。Ubuntuの`/usr/bin/python3`の置換は不要。以降の本番アプリ操作は`file-scan`ユーザーと同じ仮想環境を使う。準備が途中で失敗した場合は、稼働中のものと区別し、今回作った不完全な`.venv`だけを確認してから再作成する。

## 4. DB・pgvector・取込テーブル

### pgvector 0.8.6

管理者の作業ディレクトリで実行する。既存のvectorパッケージと重ねて上書きせず、この新規環境の導入方法を一つに揃える。

```sh
mkdir -p "$HOME/file-scan-build"
git clone --branch v0.8.6 --depth 1 https://github.com/pgvector/pgvector.git "$HOME/file-scan-build/pgvector-0.8.6"
cd "$HOME/file-scan-build/pgvector-0.8.6"
git rev-parse HEAD
make PG_CONFIG=/usr/lib/postgresql/18/bin/pg_config OPTFLAGS=""
sudo make PG_CONFIG=/usr/lib/postgresql/18/bin/pg_config install
```

CPU固有の最適化フラグを外し、VM移動時のCPU差を減らす例。[pgvector公式ビルド方法](https://github.com/pgvector/pgvector#installation)

### PGroonga（検索APIを使う場合は必須）

Ubuntu 26.04の標準PostgreSQL 18には、公式APTの`postgresql-18-pgroonga`を使用できる。採用版をAPTで用意できない場合は固定ソースからの導入も選べる。いずれか一方を選び、実際の拡張・依存版を記録する。[検索 API の本番導入](../file-search/本番導入仕様.md)、[公式Ubuntu手順](https://pgroonga.github.io/install/ubuntu.html)

### DB作成とスキーマ導入

新規 DB の例。検証にも同じ VM を使う場合は、業務データから隔離した検証専用 DB と専用の書込可能なチェックアウトを用意する。検索 API を同じ DB で運用する場合は、取込表の後に検索表を初期化する。検索用の拡張・認証・公開は [検索 API の本番導入](../file-search/本番導入仕様.md) を参照する。

```sh
sudo -u postgres psql -v ON_ERROR_STOP=1
```

```sql
CREATE ROLE file_scan LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE;
\password file_scan
CREATE DATABASE file_scan OWNER file_scan;
CREATE DATABASE file_scan_test OWNER file_scan;
\connect file_scan
CREATE EXTENSION IF NOT EXISTS vector WITH SCHEMA public;
CREATE EXTENSION IF NOT EXISTS pgroonga WITH SCHEMA public;
\connect file_scan_test
CREATE EXTENSION IF NOT EXISTS vector WITH SCHEMA public;
CREATE EXTENSION IF NOT EXISTS pgroonga WITH SCHEMA public;
\quit
```

取込専用環境では `pgroonga` の 2 行を省略する。検証用 DB を分けた VM で運用する場合、当該 DB の作成と拡張はそちらで行う。次は DB ロール `file_scan` で TCP 接続し、新規専用 DB に配布 SQL を適用する例。

```sh
cd /opt/file-scan
psql -h 127.0.0.1 -U file_scan -d file_scan -v ON_ERROR_STOP=1 -f sql/postgresql/schema-v3.sql
psql -h 127.0.0.1 -U file_scan -d file_scan -c "SELECT version FROM winnap.schema_migrations;"
psql -h 127.0.0.1 -U file_scan -d file_scan -c "SELECT extname, extversion FROM pg_extension WHERE extname IN ('vector', 'pgroonga');"
```

新規 SQL は `winnap` に取込用 20 表を作成し、管理版を 3 にする。SQL を使う代わりに、接続設定後に `file_scan_admin /opt/file-scan/.venv/bin/file-scan init-db --config /opt/file-scan/config.local.yaml` でも、事前に `vector` を有効にした新規 DB を初期化できる。既存 DB の手順は [バックアップ、復旧と移行](#recovery) を参照する。DB 接続は Ubuntu 内の `127.0.0.1:5432` を指定する。

`file_scan` はこの構成では対象 DB の所有者で、拡張導入は管理者 `postgres` が行う。権限を分離する構成では、DDL 用ロールにスキーマ作成権限、実行ロールに `winnap` の `USAGE` と必要な表・シーケンス権限を付与する。検索を導入する場合、検索管理 CLI と API の権限要件も確認する。

PostgreSQL は同一 VM からの接続に限定し、TCP 接続には SCRAM 認証を使う。`pg_lsclusters` と `SHOW config_file`、`SHOW hba_file` で実際のクラスタ名と設定ファイルを確認する。配布 SQL の適用前に `psql -h 127.0.0.1 -U file_scan -d file_scan -c 'SELECT current_user, current_database()'` で対象を確認する。[PostgreSQL のクライアント認証](https://www.postgresql.org/docs/18/client-authentication.html)

## 5. 設定・モデル・辞書

設定ファイルは`/opt/file-scan/`直下に置く。YAML内の相対パスは、設定ファイルの親ディレクトリが基準となる。次は新規作成時の例。管理者がDBパスワードと必要に応じてAPIキーを設定する。既存ファイルは上書きせず所有者とモードを確認する。検索APIも運用する場合は、同じ`config.local.yaml`と取込用`.env`を引き継ぎ、API用`.env.search`を追加する。[検索 API の本番導入](../file-search/本番導入仕様.md)

```sh
cd /opt/file-scan
if [ ! -e config.local.yaml ]; then
  sudo install -o root -g file-scan -m 0640 config.example.yaml config.local.yaml
fi
if [ ! -e .env ]; then
  sudo install -o root -g root -m 0600 /dev/null .env
fi
sudoedit /opt/file-scan/config.local.yaml /opt/file-scan/.env
```

`.env` には DB 接続先とキャッシュを設定する。外部 API を使う場合は実キーを追加する。`PASSWORD` は実値を URL 用にエンコードして指定する。CLI を直接呼ぶ場合は実行環境から変数を渡す。`FILE_SCAN_DATABASE_URL` は YAML の `database_url` より優先される。

```dotenv
FILE_SCAN_DATABASE_URL=postgresql+psycopg://file_scan:PASSWORD@127.0.0.1:5432/file_scan
TIKTOKEN_CACHE_DIR=/var/cache/file-scan/tiktoken
HF_HOME=/var/cache/file-scan/huggingface
```

`config.local.yaml`では保管先とモデル配置先を絶対パスにする。

```yaml
storage_dir: /var/lib/file-scan/storage
report_dir: /var/lib/file-scan/reports
docling_artifacts_path: /var/lib/file-scan/models/docling
pdf_backend: docling
pdf_ocr:
  enabled: true
  mode: auto
  scale: 3.0
  timeout_seconds: 1800
```

手動操作ではBashセッションで以下の関数を定義する。systemdがroot所有の`.env`を環境変数として読み、コマンドは`file-scan`ユーザーで実行する。[systemd-runの仕様](https://www.freedesktop.org/software/systemd/man/latest/systemd-run.html)、[EnvironmentFileの仕様](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html#EnvironmentFile=)

```sh
file_scan_admin() {
  sudo systemd-run --wait --pipe --collect --quiet --expand-environment=no \
    --property=User=file-scan --property=Group=file-scan --property=UMask=0077 \
    --property=WorkingDirectory=/opt/file-scan \
    --property=EnvironmentFile=/opt/file-scan/.env -- "$@"
}
```

```sh
sudo install -d -o file-scan -g file-scan /var/cache/file-scan/huggingface
file_scan_admin /opt/file-scan/.venv/bin/python /opt/file-scan/scripts/download_docling_models.py --config /opt/file-scan/config.local.yaml
file_scan_admin /opt/file-scan/.venv/bin/python /opt/file-scan/scripts/download_docling_models.py --config /opt/file-scan/config.local.yaml --verify-only
file_scan_admin /opt/file-scan/.venv/bin/python -c "from file_scan.tokens import count_tokens; print(count_tokens('Ubuntu VMの確認'))"
```

Docling のレイアウト・表モデル、RapidOCR の検出・方向分類・日本語認識の ONNX 3 点を YAML の `docling_artifacts_path` に配置する。準備コマンドはリポジトリ同梱の lock を使う。`--verify-only` で両 manifest とファイルの存在・サイズ・SHA-256 を検査する。OCR 無効時に準備するのは Docling のモデルだけ。`cl100k_base` はチャンクのトークン計数用として `TIKTOKEN_CACHE_DIR` に配置する。旧環境の OpenCV が `opencv-python-headless` を含む場合は、新しい仮想環境に固定依存を導入して切り替える。両パッケージは同じ `cv2` を提供する。[Docling の lock](../../src/file_scan/docling-models.lock.json) · [RapidOCR の lock](../../src/file_scan/rapidocr-models.lock.json)

### 任意の外部 API

運用で使う機能を有効にし、`api_key_env` が示す変数を `.env` に設定する。変数が設定されている場合は YAML の `api_key` より優先される。実キーは Git 管理の対象外に置く。

```yaml
embedding:
  enabled: true
  model: text-embedding-3-small
  dimensions: 1536
  api_key_env: OPENAI_API_KEY
  batch_size: 16
  read_batch_size: 128
  batch_max_tokens: 262112
  timeout_seconds: 60
image_analysis:
  enabled: false
  formats: [pdf, xlsx, xlsm, docx]
  model: gpt-5.4-mini-2026-03-17
  api_key_env: OPENAI_API_KEY
  render_office: true
  max_images_per_document: 20
  timeout_seconds: 60
```

この例では `embed` の検索用テキスト送信を有効化する。図の説明も利用する場合は `image_analysis.enabled: true` にし、対象形式を選ぶ。Office 図形のプレビューが必要なら Ubuntu に `libreoffice-writer`・`libreoffice-calc` と対象文書に必要なフォントを導入し、実行ユーザーの PATH に `soffice` があることを確認する。貼付画像だけを扱う場合は `render_office: false` にする。プレビューの切出しには周辺の文字が含まれることがある。対象文書と送信範囲は事前に運用側で確認する。

```sh
file_scan_admin /opt/file-scan/.venv/bin/file-scan embed --config /opt/file-scan/config.local.yaml
file_scan_admin /opt/file-scan/.venv/bin/file-scan status --config /opt/file-scan/config.local.yaml
```

部分完了や API エラーはレポートを確認する。モデル・次元を変えた場合は新しいプロファイルとして準備し、検索への公開設定も合わせる。[画像説明と Embedding の仕様](仕様書.md)

## 6. SMB 共有

VMのネットワークから共有サーバー名を解決でき、SMBのTCP 445へ到達できる構成を用意する。Windows側の共有権限・ファイル権限・ファイアウォールも、VMからの実行に合わせる。ホストのドライブ文字をUbuntuのパスへ直接指定しない。

管理者が認証ファイルを用意する。値は導入先のものへ置き換え、共有の読込用アカウントを使用する。

```sh
sudo install -d -m 700 /etc/file-scan
if [ ! -e /etc/file-scan/smb-credentials ]; then
  sudo install -m 600 /dev/null /etc/file-scan/smb-credentials
fi
sudoedit /etc/file-scan/smb-credentials
sudo install -d /mnt/file-server
id file-scan
```

認証ファイルへ次の項目を記載する。

```ini
username=SMB_USER
password=SMB_PASSWORD
domain=SMB_DOMAIN
```

ドメイン指定が不要ならdomain行を省略する。`/etc/fstab`へ次の形式で追加する。`FILE_SERVER`・`SHARE`は共有元、`UID`・`GID`は`id file-scan`で得た数値に置き換える。SMBの版は共有サーバーに対応するものを使う。

```fstab
//FILE_SERVER/SHARE /mnt/file-server cifs credentials=/etc/file-scan/smb-credentials,vers=3.1.1,ro,uid=UID,gid=GID,file_mode=0440,dir_mode=0550,_netdev,x-systemd.automount,nofail 0 0
```

```sh
sudo systemctl daemon-reload
sudo mount /mnt/file-server
findmnt /mnt/file-server
sudo -u file-scan test -r /mnt/file-server/department
findmnt -rn -t cifs -T /mnt/file-server/department
```

Ubuntuのマウント先をYAMLへ指定する。

```yaml
sources:
  - source_id: department-share
    root: /mnt/file-server/department
    recursive: true
    exclude_directories: [旧版/]
    exclude_directory_names: [BK]  # どの階層でも同名フォルダと配下を除外
    exclude_filenames: ['~$*', '*.tmp']
```

手動実行前も、マウント、共有内の読込、CIFS の実体を確認する。未マウント時に残る空ディレクトリを収集できてしまうと、既存原本が削除状態になる。autofs を使う場合も `findmnt -rn -t cifs -T` で共有の実体を確認する。[Ubuntu公式のCIFSマウント手順](https://ubuntu.com/server/docs/how-to/samba/mount-cifs-shares-permanently/)

## 7. 受入確認

公開サンプルを使う受入試験は、書込可能な検証用チェックアウトと専用 DB で行う。`config.example.yaml` を基に `config.acceptance.yaml` を作り、既定のサンプル収集元を使用し、接続先・保管先・レポート先を検証用に設定する。モデルを事前取得するか、検査済みで検証ユーザーが読める配置を指す。画像説明と Embedding は無効のまま試す。[公開サンプルの構成・取得元・SHA-256](../../examples/public-samples.json)

```sh
source .venv/bin/activate
python scripts/download_samples.py
python scripts/download_docling_models.py --config config.acceptance.yaml --verify-only
file-scan scan --config config.acceptance.yaml
file-scan init-db --config config.acceptance.yaml
file-scan ingest --config config.acceptance.yaml
file-scan status --config config.acceptance.yaml
file-scan ingest --config config.acceptance.yaml
```

| 確認 | 合格の目安 |
| --- | --- |
| 棚卸し | 既定ルートの TXT・Word・Excel・PDF 各 2 件、計 8 件が対象。列挙エラー 0。旧版フォルダと Office 一時ファイルが除外される |
| 初回登録 | `registered=8`、`failed=0`、`partial=0`。現在の文書・成功世代が各 8 件。Embedding 未実行なら対象は `pending` |
| 原本と位置 | TXT の行、Word の段落・表、Excel のシート・セルと保存済み結果、PDF のページと取得座標を、`document.json`・`review.md`・`chunks.jsonl` で少なくとも各 1 件照合 |
| 再取込 | `unchanged=8`。同じ原本の `temporary_bytes_written` は 0。選択中の世代は同じ |
| 日本語 OCR | [OCR フィクスチャ](../../tests/fixtures/ocr/README.md) の横書き文字層なし画像、運用対象のスキャン PDF、文字層と画像の混在資料で、本文・読順・数値・ページ情報を照合。対象に応じて縦書き・ルビ・表も確認 |
| 共有と再起動 | 実行ユーザーで SMB 共有を読める。再起動後に DB・共有を再確認し、ログとレポートが所定の場所に出る |

`config.acceptance.yaml` の DB URL を `FILE_SCAN_DATABASE_URL` が上書きするため、実行前に環境変数も検証用へ揃える。実 DB テスト用の `FILE_SCAN_TEST_DATABASE_URL` には専用 DB を指定する。両拡張を使う全テストでは `python scripts/test_postgres.py --tb=short` を実行する。取込専用 DB で PGroonga を省いた場合も、少なくとも以下の取込・DDL・OCR・期限のテストを実行する。

```sh

  tests/test_postgres.py tests/test_schema_sql.py tests/test_improvements.py \

  tests/test_conversion_lease.py

```

モデル、サンプルまたは検証 DB 未配置によるスキップ理由を確認する。OpenAI の自動テストは応答を模擬する。運用で外部 API が必要なら、送信可能なサンプルで実疎通・結果・課金状況を確認する。

## 8. 起動と日常運用

PostgreSQLはsystemdで起動し、共有はfstabの設定で利用する。バッチは手動または運用側で決めた実行契機から起動する。以下は共有マウントを確認してingestだけを実行する、oneshotサービスの例。定期実行時刻はここでは設定しない。

`/etc/systemd/system/file-scan-ingest.service`：

```ini
[Unit]
Description=File scan ingestion
Wants=network-online.target
After=network-online.target postgresql.service
Requires=postgresql.service
RequiresMountsFor=/mnt/file-server

[Service]
Type=oneshot
User=file-scan
Group=file-scan
WorkingDirectory=/opt/file-scan
EnvironmentFile=/opt/file-scan/.env
UMask=0077
ExecStartPre=/usr/bin/mountpoint -q /mnt/file-server
ExecStartPre=/usr/bin/test -r /mnt/file-server/department
ExecStartPre=/usr/bin/findmnt -rn -t cifs -T /mnt/file-server/department
ExecStart=/opt/file-scan/.venv/bin/file-scan ingest --config /opt/file-scan/config.local.yaml
TimeoutStartSec=infinity
KillMode=control-group
```

この例は6節の共有と実パスを設定した後で使う。`.env`は`名前=値`の形式で作り、root所有・`0600`にする。systemdが読み込み、`file-scan`で起動する取込処理へ環境変数を渡す。個別の管理操作には5節の`file_scan_admin`を使う。

```sh
sudo systemctl daemon-reload
sudo systemctl start file-scan-ingest.service
sudo systemctl status file-scan-ingest.service
sudo journalctl -u file-scan-ingest.service -n 100 --no-pager
```

部分抽出の終了コード2も確認対象になる。失敗時は実行レポートを確認する。Embeddingの自動実行はこの例に含めず、実キー・送信対象を設定した後に別途実行する。

`systemctl status` と journal の終了コードを確認し、取込レポートの `summary`、`scan_errors`、`exclusions` と文書ごとの `error_code` を見る。終了コード 2 の場合は、登録済みの文書も含めて不足箇所を確認する。設定・モデル・共有の障害を直してから再実行する。同じ原本と設定の部分抽出は `--retry-partial` で再処理する。検索利用時は Embedding を作成し、必要な世代を公開担当者が明示公開する。

| 状況 | 切り分け |
| --- | --- |
| 対象が 0 件、または `scan_incomplete` | 共有をマウントした実体とユーザーの読込権限を確認し、`scan` で対象・除外・列挙結果を確認する |
| `storage_dir` が初回と異なる | 対象 DB と保管先を確認する。移設時は [バックアップ、復旧と移行](#recovery) を参照 |
| モデル不足・改変 | 固定版を配置して `--verify-only` を実行する。再発時は実行ユーザーから読めるファイルのサイズとハッシュを確認する |
| 解析期限・メモリ | 長い PDF は文書全体の所要時間とピークメモリを測り、`pdf_ocr.timeout_seconds` や VM のメモリを調整する。OCR の途中経過はページ単位に引き継がれない |
| `interrupted_previous_run` またはジョブの占有失効 | 前回の処理時間、停止理由、モデルや API の期限を確認する。中断後は新しい試行として再実行する |
| `export_write_failed` | レポート先の書込権限・容量を直し、再実行して確定済み DB からレビュー資料を生成する |

## 9. バックアップ、復旧と移行

### 整合するバックアップを作る

取込の起動契機を止め、実行中の `ingest`、`embed`、公開管理を完了または停止してから、同じ時点の DB と保管先を取得する。検索も含めて切り替える場合は検索 API を停止する。原本・画像の保管先に加え、使用中の配布版、設定、認証情報、モデル lock、サービスとマウント設定、必要な確認レポートを保存する。秘密情報と業務原本を含むバックアップは、アクセスを制限した領域に置く。

同じ VM の管理者シェルから取得する例。バックアップ先の容量と権限を確認する。

```sh
(
  set -eu
  umask 077
  backup_root=/var/backups/file-scan
  if [ ! -d "$backup_root" ]; then
    sudo install -d -m 0700 -o "$(id -u)" -g "$(id -g)" "$backup_root"
  fi
  backup_dir="$(mktemp -d "$backup_root/snapshot.XXXXXXXX")"
  cd "$backup_dir"
  sudo -u postgres pg_dump --format=custom --dbname=file_scan > file_scan.dump
  sudo tar -C /var/lib/file-scan -cf - storage > storage.tar
  sha256sum file_scan.dump storage.tar > SHA256SUMS
  pg_restore --list file_scan.dump > restore-list.txt
  tar -tf storage.tar > storage-list.txt
  printf '%s\n' "$backup_dir"
)
```

アーカイブの一覧検査に加え、別 VM など隔離した環境で定期的に復元し、DB と保管先の整合・所要時間を確認する。[PostgreSQL 18 のバックアップ文書](https://www.postgresql.org/docs/18/backup.html)

### 復旧と切り戻し

1. 停止状態を維持し、切り替え前の DB と保管領域も退避する。復元先で元の接続用ロールと必要な拡張ライブラリを先に用意し、復元対象の配布版を揃える。
2. バックアップディレクトリで `sha256sum -c SHA256SUMS` を実行する。空の復元先 DB を作成し、管理ロールで `pg_restore --exit-on-error --dbname=復元先DB file_scan.dump` を実行する。同じ組の `storage.tar` を隔離した場所で展開して権限と保管キーを確認する。
3. 復元先が使用する絶対 `storage_dir` を DB の `winnap.ingestion_settings.storage_root` と揃える。隔離 VM で同じ絶対パスを再現できる。保管先の変更が必要なら、停止中に全実体をコピーして照合し、DB の保存先と設定を同じ保守作業で移す。標準 CLI は保存先の移設を実行しない。
4. `file-scan status` と実行ユーザーの保管物読込を確認し、原本・世代・レポートを照合する。検索導入済みの場合は `file-search status`、公開されている既知の検索と出典・画像取得も確認してから切り替える。
5. 切り替えに失敗した場合はバッチと API を停止し、退避した DB・保管先・配布版・設定を同じ組で戻す。共有のマウント、従来の文書件数と公開状態を確認後に再開する。

### 既存 DB のスキーマ更新

- `winnap` 配置の v1／v2 は、対象 DB のバックアップを取って作業を止め、`file-scan init-db` で v3 に更新する。旧 v1 には Embedding 2 表、v1／v2 には `selected_generations`・`extraction_cache`・`embedding_cache` と必要な索引が追加される。旧世代は保持し、次回 `ingest` で現在世代を選択する。
- `public` 配置は完全な取込 v3 と、導入済みなら完全な検索 v1 が移行対象。旧 `public` の v1／v2 は旧配置を扱える配布版で先に v3 に更新する。停止・バックアップ後、現在の配布版で以下を実行する。

```sh
file_scan_admin /opt/file-scan/.venv/bin/python /opt/file-scan/scripts/migrate_postgres_schema.py --config /opt/file-scan/config.local.yaml
file_scan_admin /opt/file-scan/.venv/bin/file-scan init-db --config /opt/file-scan/config.local.yaml
file_scan_admin /opt/file-scan/.venv/bin/file-scan status --config /opt/file-scan/config.local.yaml
```

移行は、対象の表だけを `ALTER TABLE ... SET SCHEMA winnap` で移し、本文、ベクトル、公開コピー、索引、制約、所有シーケンス、外部キーを保持する。既存オブジェクトとの衝突・不完全な表構成を検出すると停止し、途中失敗はトランザクションをロールバックする。移行後、検索利用時は `file-search init-db` と `file-search status` を確認する。表を直接参照する運用 SQL は `winnap` へ更新する。配置だけの移行なら、そのための再抽出・再 Embedding・再公開は不要。アプリと接続プールを再起動して運用へ戻す。[移行スクリプト](../../scripts/migrate_postgres_schema.py) · [PostgreSQL の ALTER TABLE](https://www.postgresql.org/docs/18/sql-altertable.html)

## 10. 閉域環境への資材配布

対象 VM と同じ OS・CPU・Python 3.14 の接続可能な準備環境で、事前に依存とアプリの wheel を揃える。アプリ wheel のビルドは固定依存を導入した仮想環境で実行する。

```sh
python -m pip wheel --wheel-dir artifacts/wheelhouse -r requirements/ubuntu-26.04.lock
python -m pip wheel --no-deps --no-build-isolation --wheel-dir artifacts/wheelhouse .
```

ソース・OS パッケージ・PostgreSQL 拡張に加え、wheelhouse、Docling のモデル配置全体、トークナイザー辞書、検証に使う公開サンプルを配布する。仮想環境は導入先で作成する。モデルは `model-manifest.json` と、OCR 有効時の `ocr-model-manifest.json`・`RapidOcr/` を含め、実体を通常ファイルとしてコピーする。`TIKTOKEN_CACHE_DIR` を準備環境で設定して `count_tokens()` を呼び、できたキャッシュを導入先へ移す。

```sh
python -m pip install --no-index --find-links artifacts/wheelhouse \
  -r requirements/ubuntu-26.04.lock 'file-scan[dev,search]==0.1.0'
python scripts/check_python_environment.py
python -m pip check
python scripts/download_docling_models.py --config config.local.yaml --verify-only
python -c "from file_scan.tokens import count_tokens; print(count_tokens('閉域環境の確認'))"
```

外部接続を使う機能（画像説明、文章の Embedding、検索 API の質問 Embedding、C++／Qt の文書生成）には、それぞれ指定した API の到達経路が必要。閉域で本番外部 API を利用しない取込では画像説明と Embedding を無効にする。
