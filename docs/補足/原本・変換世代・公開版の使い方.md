# 原本・変換世代・公開版の使い方

「ユーザーIDは最大何文字か」と検索したとき、どの手順書の記述が返るのでしょうか。このシステムでは、取込時のファイルを**原本**として保管し、そこから取り出した本文とその出典を**変換世代**として記録します。担当者がその世代を確認し、**公開版**に採用すると、利用者が検索して原本までたどれます。

## 同じ手順書を書き換えたとき

同梱の「ユーザー登録」には「ユーザーIDは必須です。半角英数字で最大20文字を入力します。」とあります。この上限を後日30文字に改める例で、既定の公開版を検索したときの変化を見てみます。[例に使う手順書](../../examples/input/ユーザー登録.md)

| 担当者の操作 | 取込側にあるもの | 現行検索でこの文書から返せる内容 |
| --- | --- | --- |
| 初回の手順書を取り込む | 20文字と書かれた原本と、その変換世代 | まだ未公開 |
| 抽出した記述を確認して公開する | 同じ原本・同じ世代 | 「最大20文字」。出典からその原本を開ける |
| 同じ場所の手順書を30文字に改め、再取込する | 同じ文書に新しい原本版と変換世代が加わる | 更新がDBに記録された時点で旧版は対象外。新版は公開待ち |
| 30文字の記述を確認し、新しい世代を同じ公開版に採用する | 新旧の原本版と世代が残る | 「最大30文字」。出典は新版の原本を指す |

検索APIが参照するのは取込処理がDBに記録した状態です。共有フォルダ上で編集しただけの段階では、検索には前回取り込んだ内容が反映されています。

## 何を識別するか

| 呼び方 | 何を表すか | 覚えておくID |
| --- | --- | --- |
| 原本 | 収集元から読み取り、`storage_dir` に保管したファイル。どの文書かと、その時点の中身を別々に記録する | `document_id` は収集元IDと相対パスで決まる文書ID。`source_version` はファイル全体のSHA-256（内容のハッシュ） |
| 変換世代（抽出世代） | ある原本版を特定の条件で読み取り、段落や表、検索用の短い本文（チャンク）、元のページ・行・セルなどの位置をまとめた下書き | `generation_id` は文書ID・原本版・変換条件の識別子（`conversion_revision`）の組み合わせで決まる |
| 公開版（業務リリース） | 「11月版」のように名前を付け、どの文書のどの公開コピーを検索に使うかをまとめたもの | `release_id` は版全体、`publication_id` はその版に採用する文書1件分の公開コピーを指す |

- **ファイル名や置き場所を変えた場合**は、収集元IDまたは相対パスが変わると別の文書IDになります。同じバイト列であれば原本のハッシュは共通です。
- **変換条件だけを変えた場合**も、たとえばチャンクの長さを変えて再取込すると、同じ原本版に別の変換世代ができます。同じ内容・同じ条件で正常に再取込したときは、既存の成功世代を再利用します。
- **公開する世代を選ぶとき**は、そのナレッジ（`knowledge_id`）と文書について取込処理が現在選んでいる世代を使います。DBでは `selected_generations` がその対応を持ちます。`publish` は承認した本文・位置・その時点の検索用ベクトルなどを検索側にコピーします。取込側の世代には公開後も `draft` が残ります。

## 文書を1件公開する

以下は、管理用CLIを使える環境で、例の手順書を収集元に置いて試す手順です。`config.local.yaml` はその環境の設定ファイルに読み替えてください。取込と公開には同じDB・ナレッジ・保管先を指定します。通常検索を試すには PostgreSQL の vector・PGroonga、`embedding.enabled: true`、Embedding用のAPIキーが必要です。[環境構築と公開用DBの準備](../file-search/本番導入仕様.md#publication)

### 1. 取り込んで原本と本文を照合する

```sh
file-scan init-db --config config.local.yaml
file-search init-db --config config.local.yaml
file-scan ingest --config config.local.yaml
```

最初の2行は初回のDB準備です。`ingest` の出力にある `report` を開き、`files` 配列から `relative_path` が目的の手順書に一致する行を探します。その行の `document_id`、`source_version`、`generation_id`、`processing_status` を確認します。

設定の `report_dir` の下にある `generations/<世代ハッシュ>/review.md` を開き、原本の「最大20文字」と抽出本文・行位置を照合します。フォルダ名は `generation_id` から先頭の `sha256:` を除いた値です。検索に渡す単位は同じ場所の `chunks.jsonl` で確認できます。`review.md` はDBから書き出した確認用ファイルです。本文を直すときは収集元を修正して再取込します。

### 2. 検索用ベクトルを準備し、承認した世代を公開する

```sh
file-scan embed --config config.local.yaml
file-scan status --config config.local.yaml
file-search create-release --config config.local.yaml --release manual-2026-11
file-search publish --config config.local.yaml --release manual-2026-11 \
  --document-id '<手順1の document_id>' \
  --generation-id '<手順1の generation_id>' \
  --reviewed-by '<実際の承認者ID>'
```

山括弧は実際の値に置き換え、2つのIDは `sha256:` を含めて全桁を使います。`file-scan status` の `embeddings` で対象プロファイルの `pending` が 0、`ready` が対象チャンク数に達したことを確認します。公開後にベクトルを生成した場合は、同じ世代をもう一度公開すると公開コピーにも反映されます。

`create-release` はその時点の対象文書を公開予定として登録します。採用する文書ごとに `publish` を実行し、戻り値の `publication_id` を控えます。部分抽出（`partial`）は欠けた箇所を確認したうえで `--allow-partial` を付けると公開できます。画像から生成した説明も含める場合は、原図と照合し、`--include-image-descriptions` を付けます。

### 3. 利用者に見える版と出典を確かめる

最初に作った業務版が自動で既定版になります。2つ目以降は必要な文書を公開してから、`file-search create-release --config config.local.yaml --release '<切り替え先の版名>' --make-default` で切り替えます。`file-search status --config config.local.yaml` の `catalogs[].default_release_id` と `releases` にある版名・IDを照合できます。

通常モード（`search.test_mode: false`）のAPIに問い合わせます。ローカルで試す場合は、検索用の接続キー `FILE_SCAN_SEARCH_API_KEY` を設定し、`file-search serve --config config.local.yaml` で起動します。別の端末にも同じキーを設定し、次を実行します。`demo` は設定の `knowledge_id` に、URLは起動先に合わせてください。

```sh
curl --silent --show-error --fail-with-body http://127.0.0.1:8000/search-with-status \
  -H "Authorization: Bearer $FILE_SCAN_SEARCH_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"knowledge_id":"demo","query":"ユーザーIDは最大何文字ですか","retrieval_setting":{"top_k":5,"score_threshold":0.0}}'
```

該当する `records` の `content` で引用本文を読み、`metadata.publication_id` が手順2の戻り値と一致するか確認します。`metadata.source_locations` が引用箇所、`metadata.source_ref` が保管原本を取得するためのパスです。APIのベースURLにこのパスを付け、同じ接続キーでGETすると、回答の根拠になったファイルを開けます。

現行検索では、上の例のように `target_release` を省略するか、`current` を指定します。結果が空のときは `retrieval_status` を確認してください。`pending_updates` は公開待ち・再公開待ちの文書数、`index_pending_documents` は公開コピーにベクトルが不足する文書数です。件数は版全体を表します。`coverage_state` が `complete` で `result_state` が `no_match` なら、準備の済んだ範囲でその質問に一致する根拠がありませんでした。[検索状態と応答の仕様](../file-search/仕様書.md)

## 更新・履歴・公開取り消し

**同じ公開版を更新する。** 手順1の再取込・照合からやり直し、`embed` 後に新しい世代を既存の版名で `publish` します。差し替えは文書単位です。

**改訂前の手順書も検索できるようにする。** 11月版に「最大20文字」の公開コピーを残し、12月版を作って「最大30文字」の文書を公開します。12月版を既定にすれば現行検索には30文字が出ます。履歴検索を許可して起動したAPI（`file-search serve` の `--allow-history`）では、検索リクエストの `metadata_condition.conditions` に `{"name":"target_release","comparison_operator":"is","value":"manual-2026-11"}` を指定すると、11月版で採用中の20文字の記述を参照できます。同じ11月版で差し替え済みのコピーや、収集対象から外れた文書、削除・収集失敗が確定した原本は履歴検索の対象外です。

**1文書の公開を取り消す。** 次のコマンドで、その文書が指定版の検索と原本取得の対象から外れます。原本・公開コピー・取り消し記録は残り、別の業務版で採用していれば、その版からは引き続き参照できます。

```sh
file-search unpublish --config config.local.yaml --release manual-2026-11 \
  --document-id '<対象の文書ID>' --withdrawn-by '<操作者ID>'
```

## C++・Qt の生成仕様書を公開する場合

`cpp-scan` はソース一式をスナップショット（`snap-…`）として保存し、解析して仕様書一式（`gen-…`）を生成します。`cpp-scan ingest --generation` に渡すのは、この仕様書一式の生成IDです。受け渡し後は、生成したMarkdown **1ファイルずつ**が `file-scan` の原本になります。検索結果の `source_ref` から開けるのもそのMarkdownです。

公開時は `artifact_root/state/handoffs/<run_id>.json` の `documents` から対象の `path` を選びます。そこにある **`document_id` と `extraction_generation_id`** を、それぞれ `file-search publish` の `--document-id` と `--generation-id` に渡します。ベクトル作成と公開には生成仕様書用ナレッジの設定を使います。[ソースから仕様書を生成して引き渡す手順](../cpp-scan/本番導入仕様.md) ／ [文書取込と再利用の仕様](../file-scan/仕様書.md)
