# 検索API仕様書

[機能別ドキュメント一覧](../README.md)

承認された文書から質問に関連する根拠を検索し、本文・出典・対象版・検索範囲の準備状況を返す。[機能説明資料](機能説明資料.md)に利用例、[本番導入仕様](本番導入仕様.md)に環境構築と運用手順を示す。

## 提供範囲

現行モードは `local_prototype`。1つのAPIプロセスは設定した `knowledge_id` を扱い、検索と原本・画像の取得には共有接続キーを要求する。文書ACL・利用者別SSOは未実装で、状態の `access_control` は `not_enforced`、`policy_revision` は `null`。接続元はナレッジ内の公開資料を共有できる範囲に限定する。Dify本体、Chatflow、回答用LLMは別途構成する。

| メソッド・パス | 動作 |
| --- | --- |
| `POST /search-with-status` | 根拠と検索状態を返す。検索自体が成功すれば、対象範囲の準備不足や返却予算不足も200の状態として返す |
| `POST /retrieval` | Dify External Knowledge API互換。成功時は `{"records":[…]}`。準備不足・返却予算不足は409 |
| `GET /sources/{publication_id}` | 版で採用中の原本を取得 |
| `GET /sources/{publication_id}/images/{occurrence_id}` | 公開コピーに凍結した画像出現から画像を取得 |
| `GET /healthz` | DB接続、検索スキーマv1、vector・PGroonga、必須索引を確認。正常時は `status: ok` と `execution_mode` 等を返す |
| `GET /docs`、`GET /openapi.json` | FastAPIのAPI定義。導入例では `/healthz` とともにVM内から確認 |

## 入力

両POSTに `Authorization: Bearer <接続キー>` と `Content-Type: application/json` を指定する。圧縮を含む `Content-Encoding` を送らない。本文の上限は32 KiB。未知の項目や暗黙の型変換を拒否する。

```json
{
  "knowledge_id": "business-docs",
  "query": "日次締め E1203 が発生する条件は？",
  "retrieval_setting": {"top_k": 5, "score_threshold": 0.0},
  "metadata_condition": {
    "logical_operator": "and",
    "conditions": [
      {"name": "target_release", "comparison_operator": "is", "value": "current"},
      {"name": "artifact_type", "comparison_operator": "is", "value": "source"}
    ]
  }
}
```

| 項目 | 許容値 |
| --- | --- |
| `knowledge_id` | 必須の文字列、1〜128文字。通常モードでは設定値と一致させる |
| `query` | 必須の文字列、1〜4000文字。通常モードでは追加で2048トークン以内 |
| `retrieval_setting.top_k` | 必須の整数、1〜20。文脈を含む |
| `retrieval_setting.score_threshold` | 必須の有限数、0〜1。RRFスコアへ適用する下限 |
| `metadata_condition` | 省略・`null`・オブジェクト。オブジェクトの場合は `conditions` が必須で、空配列も有効。論理演算子は `and`、省略時も `and` |

各条件名は1回まで。配列の型上限は8件で、現行の許可名は次の4種類。値は1〜256文字の文字列、または重複のない同文字列1〜20件。空白のみの文字列とNULを拒否する。

| 条件名 | 演算子と値 | 動作 |
| --- | --- | --- |
| `target_release` | `is` と単一文字列 | 省略または `current` は既定版。版IDや版名の明示は履歴検索として扱う |
| `document_id` | `is` と単一文字列、`in` と配列 | 原本の論理IDで絞る |
| `feature_id` | `is` と単一文字列、`in` と配列 | 公開時に付けた機能ラベルのいずれかに一致。一度も機能ラベルを公開していないナレッジでは422 |
| `artifact_type` | `is` と単一文字列、`in` と配列 | `source`（原資料由来）または `derived`（派生説明）で絞る |

### 対象版と更新

- 既定版は `search_mode: current`。その版の採用コピーが最新の原本ハッシュ、選択世代、変換設定、世代更新時刻、Embeddingプロファイルと一致する場合に採用する。現在含まれる原本の台帳を参照する。
- 明示版は既定版と同じIDでも `search_mode: history`。起動時に `--allow-history` を指定したときに有効となる。その版に登録され、現在も採用中の公開コピーが対象となる。廃止したコピー、資料範囲から外れた原本、削除・利用不能・収集失敗の原本は対象外。
- APIは取込側がDBに確定した状態を読む。原本が更新されたときは再公開まで現行候補から外れる。未変更原本の再取込中や再取込の中断時は確定済みの状態を読み続ける。収集失敗の判定はナレッジ単位で管理する。
- 公開管理は取込と共通のロックを使い、コピー作成と採用参照の変更を同一トランザクションで行う。検索時はDBを `REPEATABLE READ` で読み取り、質問Embedding中はDB接続を手放す。返却前の再照合で版・公開・収集台帳が処理中に変化した場合は503。

## 検索と根拠の組み立て

公開コピーの候補に版・原本・フィルターを適用し、3経路それぞれ最大50件を得る。

| 経路 | 現在の検索方式 |
| --- | --- |
| 意味 | 採用済みプロファイルのOpenAIモデル・次元数で質問をベクトル化。pgvectorのcosine距離で正確検索する。`search.semantic_min_cosine_similarity` は0〜1、既定値0.0のときも類似度が正の候補に限る |
| 全文 | PGroongaの `TokenBigram` と `NormalizerAuto` で質問を分割。2〜128文字の語を重複なしで最大16個取り、リテラルの `&@` をORで組み合わせる。PGroongaの生スコア順で候補を取る |
| 識別子 | バッククォート内の語を優先し、英字またはアンダースコアで始まる識別子と合わせて最大16個抽出する。大文字小文字・識別子内の記号を保持し、末尾のピリオド・コロン・スラッシュを除いた文字列を公開チャンクの配列に完全一致させる。一致数の降順で候補を取る |

フィルター適用後の公開チャンクがゼロなら、質問Embeddingを省略して対象版全体の準備状況を計算する。候補があるときにDB・Embedding・必須経路が使えない場合は503または504。正常な結果は順位を統合して返す。RRF（Reciprocal Rank Fusion）は各経路の順位 `r` に `1 / (60 + r)` を加算し、`3 / 61` で割って0〜1のスコアにする。スコア版は `rrf-bound-v1`。`score_threshold` 以上の候補を返却対象とする。

- `top_k` のうち最大 `min(5, floor(top_k / 3))` 件を文脈に使う。親・確認済み関係・直前見出し・表ヘッダー・後続ブロックを、同一公開コピーかつ同じ由来で1段だけ補完する。空いた枠は後続のヒットに使う。ヒットは原本ごとに最大3件。
- 1レコード2000トークン、全体6000トークン、状態を含めたJSON全体256 KiB。引用の短縮後も元ブロックの文字範囲が追える。表を切り詰める必要がある場合は候補を除外して次を試す。JSONサイズ調整で支持ヒットを除いたときは、その文脈も除く。
- レコード順はスコア降順、同点は `evidence_id` の辞書順。文脈のスコアは支持ヒットから引き継ぐ。

## 応答

`POST /search-with-status` の成功時は `api_version: "1"`、`request_id`（UUID）、`records` と `retrieval_status` を返す。検索応答の `X-Request-ID` は `request_id` と同じ値。

各レコードは `content`（引用本文）、`score`（0〜1）、`title`（表示名）、`metadata`（オブジェクト）を持つ。通常モードのメタデータは次のとおり。

| メタデータ | 内容 |
| --- | --- |
| `evidence_id`、`evidence_role` | 世代・チャンク・引用範囲等から算出したID。役割は `hit` または `context` |
| `document_id`、`source_version`、`generation_id`、`conversion_revision` | 原本の論理ID、原本ハッシュ、変換世代、変換設定等の識別子 |
| `publication_id`、`target_release`、`publication_state` | 公開コピーID、業務版ID、`published` |
| `chunk_id`、`block_ids`、`quality_flags` | 対応するチャンク、ブロック、品質フラグ。文脈のブロックには `chunk_id` が付かない |
| `artifact_type`、`score_version`、`excerpted` | `source` / `derived`、スコア算出方式、本文を抜粋したかどうか |
| `source_locations`、`location_granularity` | 原本上の出典。ファイル種別に応じて行・ページ・シート・セル範囲等を保持し、表示粒度は `block`。行を絞り込める場合は引用範囲に合わせる |
| `source_spans`、`description_spans` | 原資料の対応範囲は `source_spans`。派生説明は `source_spans: []` と `description_spans`。範囲はチャンクとブロックそれぞれの0始まり・終端を含まない文字位置 |
| `related_evidence_ids`、`supporting_hit_ids` | 補完文脈と支持ヒットの対応。後者は文脈レコードに付く |
| `source_ref`、`related_assets` | 原本のAPI相対URLと画像等の出現情報（最大10件）。画像として取得できる要素に `image_ref` が付く |

### 対象範囲の準備状況と結果状態

| `retrieval_status` の項目 | 値・意味 |
| --- | --- |
| `snapshot_id`、`resolved_release_id` | この応答の読み取り識別子（UUID）、解決した業務版ID |
| `catalog_revision`、`publication_revision` | 取込台帳と公開カタログの更新番号 |
| `search_mode`、`execution_mode` | `current` / `history`、`local_prototype` / `test` |
| `access_control`、`policy_revision` | 現行は `not_enforced`、`null` |
| `embedding_profile_id`、`search_config_version` | 採用Embeddingプロファイル、現行検索設定 `poc-v2` |
| `coverage_scope`、`coverage_state` | 通常は `configured_knowledge_release`。不足なしは `complete`、不足ありは `incomplete`、収集状態や版対応が未確定なら `unknown` |
| `result_state` | レコードありは `matched`、閾値を通過した候補なしは `no_match`、候補が予算で1件も返せないときは `budget_exhausted` |
| `returned_records`、`limit_reasons`、`message` | 返却件数、制約の理由（`top_k`、`document_cap`、`token_budget`、`context_limit`、`response_size`）、表示用の状態説明 |

`coverage` は `document_id` 等の追加フィルター適用前の版全体で計算する。各件数は `pending_updates`（未公開・再公開待ち）、`failed_documents`（原本・収集・現行変換の失敗）、`partial_documents`（承認済み部分抽出）、`uncollected_documents`（収集未完了）、`index_pending_documents`（公開チャンクにベクトルが欠ける原本）、`unknown_documents`（版対応未確定）。ナレッジの収集ステータスが `succeeded` 以外の場合は件数を `null` とする。部分抽出とベクトル不足など、同じ原本が複数の件数に含まれる場合がある。

`POST /retrieval` は通常モードで `coverage_state=complete` かつ `result_state` が `matched` または `no_match` なら200。準備不足と予算不足が重なる場合は `COVERAGE_NOT_COMPLETE` を先に返す。空の結果を受け取ったときは、その質問で返せる根拠が得られなかった旨を扱う。

### 原本・画像の取得

APIのベースURLへ `source_ref` または `related_assets[].image_ref` を付け、検索と同じBearerキーを付けてGETする。画像は `original_image` または `region_image` の凍結済み出現を使う。履歴参照は返却された `?mode=history` を保持する。現行・履歴とも取得時の採用状況を確認し、CASの実体をSHA-256とサイズで検証してから添付として配信する。対象外は404、保管ルートの不整合や実体の検証失敗は503。画像と原本のバイト列は検索応答と別に取得する。

### エラーと制限

両POSTのAPIエラーは整数の `error_code`、機械判定用の `code`、`error_msg`、`request_id`、`retryable` を返す。

| HTTP | `code` | 整数 | 主な原因 |
| --- | --- | ---: | --- |
| 401 | `UNAUTHENTICATED` | 1002 | 接続キーなし、不一致 |
| 404 | `SCOPE_NOT_FOUND` | 2001 | ナレッジ・業務版・原本参照の範囲外、履歴未許可 |
| 409 | `RELEASE_UNRESOLVED` | 3001 | 既定版を解決できない |
| 409 | `COVERAGE_NOT_COMPLETE` | 3002 | 互換APIで対象範囲の準備不足 |
| 409 | `RESULT_BUDGET_EXHAUSTED` | 3003 | 互換APIで根拠を返却予算内に収められない |
| 413 | `REQUEST_TOO_LARGE` | 4001 | 本文サイズ上限超過 |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | 4002 | JSON以外、または `Content-Encoding` あり |
| 422 | `INVALID_REQUEST` | 4003 | JSON・型・範囲・フィルター不正 |
| 429 | `RATE_LIMITED` | 5001 | 同時実行枠の取得失敗。`Retry-After: 1` 付き |
| 503 | `SEARCH_UNAVAILABLE` | 5002 | DB・索引・Embedding・保管実体の障害、処理中の公開状態変更等 |
| 504 | `SEARCH_TIMEOUT` | 5003 | 全体期限、Embedding、DBプール待ち、SQLキャンセル |
| 500 | `INTERNAL_ERROR` | 9001 | 想定外の処理障害 |

検索期限は本文受信から応答開始まで10秒。質問Embeddingは4秒、SQLの `statement_timeout` は2秒、DB接続・プール待ちと検索枠待ちは各1秒。1プロセスあたり同時検索は4件で、DBプールも4接続。OpenAI SDKの再試行は0。期限や接続切断を検知すると検索処理をキャンセルする。成功応答と一部の失敗は、本文・鍵・生SQLを含めず `search_events` に記録する。

両POSTの504には `stage`（例 `query_embedding`、`fulltext_search`、`freshness_check`）、`timeout_kind`（`request_deadline`、`embedding_timeout`、`db_pool_timeout`、`db_query_cancelled` のいずれか）、`elapsed_ms` が加わる。再試行は `retryable`、呼出側の残り時間と `Retry-After` を考慮する。詳しいログ照合は[504の切り分け](本番導入仕様.md#timeout-diagnostics)を参照する。

## 管理CLI

### 版の作成と公開

取込用の接続で `file-scan init-db`、`file-search init-db`、`file-scan ingest`、`file-scan embed` を同じYAMLで実行する。運用での実行環境と権限は[本番導入仕様](本番導入仕様.md)を参照する。管理用の例を示す。

```sh
file-search create-release --config config.local.yaml --release release-2026
file-search publish --config config.local.yaml --release release-2026 \
  --document-id 'sha256:<対象原本の論理ID>' \
  --generation-id 'sha256:<承認した変換世代ID>' \
  --reviewed-by '<承認者ID>'
file-search status --config config.local.yaml
```

- `create-release` は現時点の取込範囲を予定原本として登録する。初回の版は自動で既定になる。後続の版は資料の公開確認後、同じ版名の `create-release --make-default` で切り替える。予約名 `current` は業務版名に使えない。
- `publish` へは原本・世代レポートのIDを渡す。現在の選択世代との一致、原本実体、チャンク・ブロックの対応、既存ベクトルの入力ハッシュ・次元数を検査する。処理結果が部分抽出なら追加で `--allow-partial` が必要。原図と照合した画像説明を含めるときは `--include-image-descriptions` を指定する。機能ラベルは `--feature-id` を最大20回指定できる。
- 取込データの公開状態は `draft` のまま。承認済みチャンク・ブロック・出典・画像参照・関係・ベクトルを検索表に凍結する。公開後に `embed` した場合は再公開してベクトルを反映する。コピーの入力が同一なら公開IDを再利用する。既存の検索カタログへ別のEmbeddingモデル・次元数を混在させる操作は拒否する。
- `status` は設定ナレッジのカタログ・登録版を表示する。個々の検索時点の準備状況は `/search-with-status` を確認する。

### 公開の取り消し

```sh
file-search unpublish --config config.local.yaml --release release-2026 \
  --document-id 'sha256:<対象原本の論理ID>' --withdrawn-by '<操作者ID>'
```

対象版の採用参照だけを解除する。その版の検索と原本・画像取得から外れ、予定原本は準備状況に残る。原本・公開コピー・別の版の採用は保持する。変更は `search_events` に `publication_withdrawn` として記録される。登録済みで採用されていない原本への操作は `changed: false`。再採用には検査と承認のうえで `publish` を実行する。

## DBを使わない接続試験

`FILE_SCAN_SEARCH_API_KEY` を設定し、`file-search serve --config config.search-test.example.yaml --port 8000` で起動する。`serve` は `127.0.0.1` で待ち受ける。通常モードへの切り替えは、`search.test_mode: false`（既定）の設定を使って再起動する。

テストモードでは、両POSTが入力形式・文字数・本文バイト数・Bearerキーを検査し、「これは検索APIのテスト応答です。DB検索は実行していません。」を1件返す。`metadata.test_mode: true` と `evidence_role: test` が付き、状態付き応答は `execution_mode: test`、`coverage_scope: test`、`coverage_state: unknown`、版・件数等を `null` とする。`/retrieval` も200の固定応答。healthは `database: not_used` を返し、原本・画像の取得は404。DB、OpenAI、トークン計数は使用しない。版作成・公開などの管理コマンドはDBを使う。

## 保存構成

取込は `src/file_scan/`、検索・公開管理は `src/search/`。同じPostgreSQLの `winnap` スキーマを使い、取込v3と検索v1は独立した管理版を持つ。検索v1の8表は[検索スキーマ定義](../../src/search/schema.py)に従う。

| 検索v1の表 | 主な役割 |
| --- | --- |
| `search_schema_migrations` | 検索DBの版 |
| `search_catalogs` | ナレッジごとの既定版、採用Embeddingプロファイル、公開更新番号、機能ラベルの利用状態 |
| `search_releases` | 業務版の識別子と表示名 |
| `search_release_bindings` | 業務版の予定原本、期待する原本ハッシュ・変換設定、現在の採用コピー |
| `search_publications` | 版別の公開コピー、採用世代、承認、品質、ブロック間関係 |
| `search_blocks` | 公開ブロックの本文、出典・画像出現、構造と順序 |
| `search_chunks` | 検索用文字列、返却本文、対応範囲、識別子・機能ラベル、凍結したベクトル |
| `search_events` | 検索・取り消しの運用記録 |

必須索引は `ix_search_chunks_fulltext`（PGroonga、`search_text`）、`ix_search_chunks_identifiers`（GIN、`identifiers`）、`ix_search_chunks_features`（GIN、`feature_ids`）。検索とhealthは有効な索引を確認する。意味経路はpgvectorの正確検索を使う。環境構築・索引修復とバックアップは[本番導入仕様](本番導入仕様.md)に従う。
