# C++／Qt 5 ソース取込の本番導入仕様

[機能別ドキュメント一覧](../README.md)

本番では Windows ホスト上の Ubuntu 26.04 VM を使う。VM、実行ユーザー、Python 3.14、PostgreSQL 18 と pgvector、共有フォルダの準備は[ファイル取込の本番導入仕様](../file-scan/本番導入仕様.md)に従う。管理者が `/opt/file-scan/` に配備し、`file-scan` ユーザーが取込バッチを実行する。以下の本番例は管理者の Bash セッションから実行する。Windows へ直接導入する場合の UNC と Windows 実機の動作は別途確認が必要。

## Python と固定版 CodeWiki

`cpp-scan`、`file-scan`、`file-search` を同じ仮想環境に配置する。共通の本番導入手順に従って `/opt/file-scan/.venv` に Python 3.14 と統合 lock、アプリの `[dev,search]` 依存を導入してから、管理者が CodeWiki を追加する。配備済みのソースと仮想環境は root 管理とする。

```sh
cd /opt/file-scan
/opt/file-scan/.venv/bin/python -m pip check  # CodeWiki を初めて入れる前に実行
sudo /opt/file-scan/.venv/bin/python -m pip install --no-deps -r requirements/codewiki-source.txt
/opt/file-scan/.venv/bin/python scripts/check_python_environment.py --codewiki
/opt/file-scan/.venv/bin/cpp-scan --help
```

CodeWiki は `2.0.0`、コミット `1b4af43d6d20c8dbd758fe1d5f888cc6947ed11d` を使用する。[取得定義](../../requirements/codewiki-source.txt)と[使用経路の依存](../../requirements/codewiki-runtime.in)を参照。C++／JavaScript の構造解析と OpenAI 互換 API で使う依存は[統合 lock](../../requirements/ubuntu-26.04.lock)に含まれる。CodeWiki 導入後の `pip check` では MCP や他言語・他プロバイダー向け等の未導入依存が報告されるため、共通依存の `pip check` は導入前、固定版・統合 lock の照合は導入後に行う。旧設定が `codewiki.python` に専用 `.venv-codewiki` を指定している場合は、その項目を外して `cpp-scan` の Python を使う。

本番 VM から接続できる場合は次の操作でトークナイザー辞書を取得する。閉域の場合は接続可能な準備環境で取得し、本番 VM へ配布する。`analyze` も CodeWiki の初期化時に辞書を読む。本番の `TIKTOKEN_CACHE_DIR` には、共通の `/var/cache/file-scan/tiktoken` を使用する。準備済みの辞書がある場合は `file-scan` ユーザーが読めることを確認して再利用する。

```sh
sudo install -d -o file-scan -g file-scan -m 0750 /var/cache/file-scan/tiktoken
sudo -u file-scan env TIKTOKEN_CACHE_DIR=/var/cache/file-scan/tiktoken \
  /opt/file-scan/.venv/bin/python -c 'import tiktoken; tiktoken.get_encoding("cl100k_base")'
```

閉域導入では、対象 OS・CPU・Python 版に合わせた共通の wheelhouse とともに、準備環境で取得した固定コミットを含む Git リポジトリと辞書を配布する。辞書ファイル `9b5ad71b2ce5302211f9c61530b329a4922fc6a4` の名前を維持し、`/var/cache/file-scan/tiktoken/` へ配置する。

```sh
# 接続可能な準備環境
mkdir -p artifacts
git clone --bare https://github.com/FSoft-AI4Code/CodeWiki.git artifacts/codewiki.git

# 閉域の導入先。管理者が artifacts/codewiki.git を配布してから実行
cd /opt/file-scan
/opt/file-scan/.venv/bin/python -m pip check  # CodeWiki を初めて入れる前に実行
sudo /opt/file-scan/.venv/bin/python -m pip install --no-index --no-deps --no-build-isolation \
  'codewiki @ git+file:///opt/file-scan/artifacts/codewiki.git@1b4af43d6d20c8dbd758fe1d5f888cc6947ed11d'
/opt/file-scan/.venv/bin/python scripts/check_python_environment.py --codewiki
```

## 設定と配置

初回は設定例をコピーする。稼働済み環境では既存の YAML、ID、パスを引き継ぐ。相対パスの基準は各 YAML の所在。

```sh
cd /opt/file-scan
if [ ! -e config.cpp-source.local.yaml ]; then
  sudo install -o root -g file-scan -m 0640 config.cpp-source.example.yaml config.cpp-source.local.yaml
fi
if [ ! -e config.cpp-docs.local.yaml ]; then
  sudo install -o root -g file-scan -m 0640 config.cpp-docs.example.yaml config.cpp-docs.local.yaml
fi
sudo install -d -o file-scan -g file-scan -m 0750 /var/lib/file-scan/cpp-scan/qt-production \
  /var/lib/file-scan/cpp-document-reports
sudoedit /opt/file-scan/config.cpp-source.local.yaml /opt/file-scan/config.cpp-docs.local.yaml
```

| 設定 | 本番で指定する内容 |
| --- | --- |
| [C++／Qt 原本の設定例](../../config.cpp-source.example.yaml) | 版や日時を含めない固定の `project_id`、実行ユーザーが読める `source_root`、専用の `artifact_root`。DB 登録する場合は `ingestion.file_scan_config: config.cpp-docs.local.yaml` |
| [生成仕様書の設定例](../../config.cpp-docs.example.yaml) | 生成仕様書専用の `knowledge_id`・`source_id`、業務上の `system_id`・`environment`、`storage_dir`・`report_dir`・`embedding` |
| 一般文書の設定 | 同じ DB を使う場合、一般文書・生成仕様書の `storage_dir` を同じ実パスに設定し、`report_dir`・`knowledge_id`・`source_id` を用途別に設定 |

`source_root` と `artifact_root` は相互に親子関係を持たないようにする。SMB の場合は Ubuntu 内のマウント先を指定する。原本版を固定した Git アーカイブ等を展開し、入力ルート内に出力先を置かない。本番の例では `artifact_root: /var/lib/file-scan/cpp-scan/qt-production`、生成仕様書の `root: /var/lib/file-scan/cpp-scan/qt-production/handoff/current`、`storage_dir: /var/lib/file-scan/storage`、`report_dir: /var/lib/file-scan/cpp-document-reports` を指定する。実行ユーザーに原本の読取権、成果物・保管・レポート先の書込権を与え、原本と成果物のアクセスを運用担当者に制限する。

取込の収集元は `<artifact_root>/handoff/current` の 1 件だけとし、`recursive: true`、`include_extensions: [.md]`、除外設定なしとする。`knowledge_id: default` は指定できない。`storage_dir`・`report_dir` は `handoff/` の内側、祖先、同一パスのいずれも不可。ファイル型 SQLite を開発で使う場合、DB ファイルを `handoff/` の外に置く。既存 DB が記録する保管先も照合されるため、設定変更でその記録を迂回しない。

| C++／Qt の主な項目 | 既定値と変更時の確認 |
| --- | --- |
| `source_encoding`、`fallback_encoding` | `auto` で UTF-8 を優先し、CP932 へフォールバック。固定指定は `utf-8`・`cp932`、パスごとの例外は `encoding_overrides: {'legacy/*.cpp': cp932}` |
| `ui_mode`、`pro_mode` | `auto`、`reference_only`。画面方式は設定にかかわらず Widgets／QML を検出し、qmake 定義は参考入力として保存 |
| `include_tests`、`include_third_party` | いずれも `false`。独自配置は `exclude_patterns` にパス／ファイル名 glob を追加。ディレクトリに一致すれば配下の探索を省略 |
| `include_files`、`exclude_patterns` | 既定は空。リテラル参照のない必要な設定ファイルはルート相対の glob で明示 |
| `max_file_bytes`、`max_files`、`copy_retries` | C++ 原本は 10 MiB／ファイル、5 万件、コピー再試行 2 回。生成 Markdown 側の文書取込は別設定で、`max_file_bytes` の既定は 100 MiB |
| `allow_partial_ingest` | `false`。部分完了版を運用上受け入れる場合に明示する |
| `codewiki` | 現在の Python、固定版・コミット、`timeout_seconds: 3600`、`max_tokens: 8192`、`request_limit: 30`、`max_depth: 2` |
| `documentation` | `language: ja`、`provider: codewiki`。モデル・キー・接続先の環境変数名は `model_env`・`api_key_env`・`base_url_env` |

## 接続先と環境変数

本番 DB 接続は `FILE_SCAN_DATABASE_URL` で明示し、初期化・下書き登録・Embedding・検索管理が同じ DB を参照することを確認する。設定例では環境変数未設定時に組み込みのローカル DB 接続先へフォールバックするため、実行前に確認する。`generate` は `CPP_SCAN_LLM_MODEL`、`CPP_SCAN_LLM_API_KEY`、`CPP_SCAN_LLM_BASE_URL` を使う。管理者が `sudoedit /opt/file-scan/.env` で、root 所有・`0600` の共通環境ファイルに LLM 用の変数を追加する。既存の DB 接続先と `TIKTOKEN_CACHE_DIR=/var/cache/file-scan/tiktoken` を引き継ぎ、必要な CA・プロキシ設定もここに記載する。モデル ID、キー、接続先は社内の実値へ置き換える。

```ini
CPP_SCAN_LLM_MODEL=<社内モデルID>
CPP_SCAN_LLM_API_KEY=<社内認証キー>
CPP_SCAN_LLM_BASE_URL=https://llm.example.internal/v1
```

systemd が環境ファイルを読み、コマンドを `file-scan` ユーザーで実行する。管理者の Bash セッションで次の関数を定義する。

```sh
file_scan_admin() {
  sudo systemd-run --wait --pipe --collect --quiet --expand-environment=no \
    --property=User=file-scan --property=Group=file-scan \
    --property=WorkingDirectory=/opt/file-scan \
    --property=EnvironmentFile=/opt/file-scan/.env -- "$@"
}
```

OpenAI に直接接続する設定例は `CPP_SCAN_LLM_BASE_URL=https://api.openai.com/v1`。モデル ID が `gpt-6.1-terra` の場合、分類・ツール利用を伴う生成で Responses API を使用し、`store: false` を指定する。ツール結果と継続に必要な暗号化済み推論情報を後続リクエストに渡す。他のモデル ID は Chat Completions 経路を使う。実接続では、ソースの送信可否、モデル・API 方式、利用枠を確認する。出力トークンとリクエストの制限は各応答／エージェントへの制限であり、プロジェクト全体の予算は API ゲートウェイ等で設定する。

辞書取得には `REQUESTS_CA_BUNDLE`、SDK の HTTPS 接続には `SSL_CERT_FILE` または `SSL_CERT_DIR` を使用できる。後者の両方が未設定の場合、`generate` の子プロセスは `REQUESTS_CA_BUNDLE` から SDK に CA の場所を引き継ぐ。プロキシは `HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY`、`NO_PROXY` と各小文字表記を子プロセスが受け取る。`NO_PROXY` に該当する API 接続はプロキシを経由しない。LLM キーは環境変数で子プロセスに渡し、CodeWiki の引数・処理出力・生成設定には保存しない。子プロセスには専用 HOME を使い、通常ログにはソース本文・認証値・外部例外全文を出さない。

## 棚卸しから下書き登録

前節の `file_scan_admin` で以下を起動する。最初は同梱の [Qt 5 サンプル](../../examples/qt5-source/README.md)で範囲と出力を確認し、本番は承認済みソースの固定版へ切り替える。サンプルと本番は別の ID と成果物領域で管理する。コードブロックは工程ごとに実行し、出力 JSON の `status` と終了コードを確認して次へ進む。

```sh
file_scan_admin /opt/file-scan/.venv/bin/cpp-scan scan --config /opt/file-scan/config.cpp-source.local.yaml
file_scan_admin /opt/file-scan/.venv/bin/cpp-scan analyze --config /opt/file-scan/config.cpp-source.local.yaml
file_scan_admin /opt/file-scan/.venv/bin/cpp-scan status --config /opt/file-scan/config.cpp-source.local.yaml
```

`analyze` の JSON に出る `analysis_id` を全桁指定する。最後に選択された解析版を使う場合は `status` の `selected.analysis` と対応する manifest を確認する。

```sh
analysis_id='<analyze の analysis_id>'
file_scan_admin /opt/file-scan/.venv/bin/cpp-scan generate --config /opt/file-scan/config.cpp-source.local.yaml --analysis "$analysis_id"
```

`generations/<generation_id>/` の `quality-report.json`、`usage.json`、`review.md`、`documents/overview.md`、`documents/unknowns.md` を確認する。画面・接続・プラグインなどの説明を原本と照合し、未確認事項を確認する。その後、既存文書 DB のスキーマ状態と保管先を確認する。共通導入で初期化済みの場合は `init-db` を省略する。

```sh
file_scan_admin /opt/file-scan/.venv/bin/file-scan init-db --config /opt/file-scan/config.cpp-docs.local.yaml  # 初回のみ。対象 DB を確認して実行
file_scan_admin /opt/file-scan/.venv/bin/file-scan status --config /opt/file-scan/config.cpp-docs.local.yaml
generation_id='<generate の generation_id>'
file_scan_admin /opt/file-scan/.venv/bin/cpp-scan ingest --config /opt/file-scan/config.cpp-source.local.yaml --generation "$generation_id"
file_scan_admin /opt/file-scan/.venv/bin/cpp-scan status --config /opt/file-scan/config.cpp-source.local.yaml
```

`state/handoffs/<run_id>.json` の文書一式、ハッシュ、文書 ID、抽出世代を確認する。取込だけで検索の公開状態は更新されない。

## Embedding と検索公開

生成仕様書側の `embedding.enabled` を有効化し、`OPENAI_API_KEY` を設定する。既定は `text-embedding-3-small`、1536 次元。一般文書側の設定を変更していても生成仕様書側へ自動継承されない。検索 DB の準備と業務版の選択は[検索 API の本番導入仕様](../file-search/本番導入仕様.md)に従う。

```sh
file_scan_admin /opt/file-scan/.venv/bin/file-scan embed --config /opt/file-scan/config.cpp-docs.local.yaml
file_scan_admin /opt/file-scan/.venv/bin/file-scan status --config /opt/file-scan/config.cpp-docs.local.yaml
file_scan_admin /opt/file-scan/.venv/bin/file-search create-release --config /opt/file-scan/config.cpp-docs.local.yaml --release '<新規業務版>'
file_scan_admin /opt/file-scan/.venv/bin/file-search publish --config /opt/file-scan/config.cpp-docs.local.yaml \
  --release '<業務版>' \
  --document-id '<受渡し結果の document_id>' \
  --generation-id '<受渡し結果の extraction_generation_id>' \
  --reviewed-by '<承認者ID>'
file_scan_admin /opt/file-scan/.venv/bin/file-search status --config /opt/file-scan/config.cpp-docs.local.yaml
```

`create-release` は新しい業務版を作る場合に実行する。採用する各文書を個別に公開し、対象ナレッジ・業務版で検索でき、出典が生成 Markdown を指すことを確認する。更新文書は再公開まで現行の検索範囲が不足し得る。Embedding を公開後にやり直した場合は同じ抽出世代を再公開してベクトルを反映する。

## 更新、中断と復旧

| 状況 | 確認と復旧 |
| --- | --- |
| `scan`・`analyze` が部分完了 | `status` と対象レポートを確認。権限、文字コード、対象上限、参照先 JSON、入力の途中変更を修正し、固定入力から再実行する。保存済み原本を再解析する場合は `analyze` に `--snapshot <snapshot_id>` を指定する |
| `codewiki_not_installed`、版・コミット不一致、`ModuleNotFoundError` | 実行中の仮想環境と Python を確認し、固定版・依存を確認し、`/opt/file-scan` で `.venv/bin/python scripts/check_python_environment.py --codewiki` を実行する |
| 辞書の取得・初期化に失敗 | `codewiki_tokenizer_download_failed` は接続可能な環境でキャッシュを作成して配置。`codewiki_tokenizer_cache_invalid` はパス・権限・辞書を確認。取得時の証明書エラーは配布された社内 CA を指定する |
| LLM の接続・TLS・プロキシ・DNS エラー | `codewiki_llm_*_failed` の種別に応じ、実行シェルの接続先、CA、プロキシの認証・接続許可、名前解決を確認する。`codewiki_timeout` は子プロセスが期限を超過。工程記録と処理規模を確認する |
| API 400・401・403・404・429、`codewiki_llm_quota_exhausted` | 順に API 方式、認証キー、権限、モデル／接続先、レート制限・利用枠を確認。利用枠不足は請求設定と API プロジェクトも確認し、修正後に同じ解析版を指定して再生成する |
| スキーマ・保管先の検査で停止 | 同じ `file_scan_admin` で生成仕様書設定の `file-scan status` を実行し、接続先と保管先を確認。`init-db` が必要な場合は対象 DB を確認して実施後、同じ生成版で再試行する |
| `ingestion_output_overlaps_handoff` 等 | 原本・受渡しと保管先・レポートが重複しないよう実パスを確認。ファイル型 SQLite の DB パスも確認する。設定と既存 DB の検証が通るまで中断復旧は行われない |
| 入力元・収集範囲変更または既存文書の削除候補 | `status` の `latest.ingest.scope_change` と `latest.ingest.planned_removals`、生成 manifest を確認。意図した変更は同じ完全版の `ingest` に `--accept-scope-change` を付けて適用。従来の受渡し状態に原本ルートが記録されていない場合もこの確認を行う |
| 部分完了の生成版 | 原則は欠落を直して再生成。例外的に `allow_partial_ingest: true` で登録する場合は `retained_paths` の旧文書を確認する。部分完了版では範囲変更を承認できない |
| 配置または DB 取込中の中断 | `state/handoff-journal.json` と `status` を確認。`preparing` は次回の `ingest` で前回配置を復元する。`ingesting` は `current/` を保持して同じ生成版を再取込し、文書ごとの確定状態を照合する。既存の部分抽出を再試行する場合は `--retry-partial` を使う |
| `interrupted_handoff_missing_current` | 取込開始後の配置元が不足している。生成 manifest、受渡し状態、DB と既存のバックアップを照合し、該当する配置内容とパスを確認して復旧する。DB の確定状況を確認できるまで、フォルダだけ旧版へ戻す操作は行わない |
| 成果物ハッシュ不一致、パス・根拠の検証エラー | 対象のバージョンと manifest を確認。改変された成果物は隔離し、整合したバックアップから復元するか、新しいスナップショット／解析／生成版を作る。保存済みバージョンの中身は手修正しない |

完成した同一条件の版を再実行すると再利用される。新しい解析版または生成版が必要な場合は対象工程に `--force` を付ける。本番の保全対象は原本・解析・生成版と状態を含む `artifact_root`、ならびに文書取込 DB と `storage_dir` の組。取込サービスと手動操作が同じ成果物を変更しない時間にスナップショットを取得し、復元時は各 manifest と受渡し記録の対応を確認する。

## 受入確認

- [Qt 5 サンプル](../../examples/qt5-source/README.md)で Widgets／QML、プラグイン JSON、接続式、根拠のファイル・行を確認する。社内ソースでは CP932、除外範囲、代表画面・プラグインをレビュー対象に含める。
- 同じ条件で再実行し、版の再利用と、変更のない文書の文書 ID・選択抽出世代・公開状態の維持を確認する。別環境で意図した差分・除外・中断時の確認を行う。
- 本番同等の DB で下書き登録・Embedding・公開を実施し、対象業務版の検索応答、出典の Markdown、更新後の再公開まで確認する。共有マウント、組織の CA・プロキシ、実モデルの品質・所要時間・料金を導入先で確認する。
- 自動検証はソース一式と統合仮想環境を揃えた検証用のチェックアウトで次を実行する。固定版 CodeWiki・辞書が揃った環境では、構造解析とローカルの固定応答 API を使う生成も対象になる。PostgreSQL の試験を実行する場合は専用テスト DB を設定する。

```sh
export TIKTOKEN_CACHE_DIR="$PWD/data/models/tiktoken"
python -m pytest tests/test_cpp_scan.py -q
python -m ruff check src tests scripts
```
