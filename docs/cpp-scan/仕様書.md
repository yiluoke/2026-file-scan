# C++／Qt 5 ソース取込仕様書

[機能別ドキュメント一覧](../README.md)

`cpp-scan` は、C++／Qt 5 のソースから根拠付きの日本語 Markdown を生成し、既存の `file-scan` に下書きとして登録する。検索対象は生成仕様書で、引用先も生成 Markdown とする。C++ 原本と中間 JSON は `cpp-scan` の成果物領域で管理する。操作例は[機能説明資料](機能説明資料.md)、設定と復旧は[本番導入仕様](本番導入仕様.md)を参照。

## 処理と境界

| 工程 | 入出力と責務 | 接続先 |
| --- | --- | --- |
| `scan` | 入力ルートを棚卸しし、対象・除外理由・障害・Widgets／QML 検出を `state/scans/<run_id>.json` に保存 | 原本フォルダ |
| `analyze` | 入力を固定し、CodeWiki の構造解析と Qt の補完結果を保存。`--snapshot` で保存済み原本を指定可能 | 原本または保存済みスナップショット |
| `generate --analysis <analysis_id>` | 指定した解析版から日本語 Markdown を生成し、文書一式と根拠を機械検証 | 設定済みの LLM API |
| `ingest --generation <generation_id>` | 検証済み Markdown を専用収集先へ配置し、既存の文書取込で下書き登録 | 文書取込 DB |
| `status` | 工程別の最新結果、選択版、直近の受渡しを表示 | ローカルの状態ファイル |

Qt／SDK の導入とビルドは開始条件に含まれない。`.pro`・`.pri`・`.prf` は参考資料として保存し、変更を検出する。qmake の設定評価、カスタムターゲットの実行、アプリ起動は対象外。DB スキーマは既存の文書取込と共通。Embedding と検索公開はそれぞれ別の明示操作とする。

## 収集と原本の固定

| 区分 | 対象 |
| --- | --- |
| C／C++ | `.c`、`.cpp`、`.cc`、`.cxx`、`.c++` とヘッダー・インライン系 `.h`、`.hpp`、`.hxx`、`.hh`、`.h++`、`.ipp`、`.inl`、`.tpp` |
| Qt | `.ui`、`.qml`、`.js`、`qmldir`、`.qmltypes`、`.qrc`、qmake 参照ファイル |
| 参考文書 | README 等の既知ファイル名、`.md`、`.markdown`、`.txt`、`.rst`、`.qss` |
| 設定 | C++／QML／JavaScript からリテラル参照されたものか、`include_files` で明示した `.json`、`.ini`、`.xml`、`.conf`、`.cfg`、`.yaml`、`.yml` |

リンク・ジャンクション、隠しファイル、既知のビルド成果物・依存ディレクトリ、`ui_`・`moc_`・`qrc_` で始まる Qt 生成ソースは除外する。テストとサードパーティーは既知のディレクトリ名で判定し、既定で除外する。独自の配置は `exclude_patterns` で指定する。利用不能なディレクトリ、必須メタデータの欠落、読み取り失敗などは除外と区別して記録する。

スナップショットは原本バイト列、SHA-256、UTF-8 作業コピー、文字コード・BOM・改行情報と原本バイト位置への行対応表を保持する。標準設定は UTF-8 優先で、失敗時は CP932 を使う。パス別の指定を優先する。デコードに失敗してもコピー済みの原本を保持し、当該ファイルを解析範囲の欠落として扱う。コピー後に一覧と内容を再照合するため、収集中の追加・消失・内容変更を検出できる。通常フォルダの再照合では全ファイルが同一時点に属することを保証できないため、版を固定した Git アーカイブ等を本番入力に使う。

## 構造解析と Qt 補完

固定版 CodeWiki の `DependencyGraphBuilder` を LLM 接続なしで呼び、Tree-sitter が取得した構成要素、位置、依存候補を正規化する。C++ マクロ回復後も構文エラー候補が残る場合は件数を記録し、構造を取得できなかったエラーファイルを部分失敗とする。

| 領域 | ソース上で確認する情報 | レビュー項目 |
| --- | --- | --- |
| C++ 構造・API | クラス、関数、依存関係の候補、ファイルと行範囲 | 型・オーバーロード・実際の呼出先 |
| Widgets | `.ui` の画面クラス、`objectName`、テキスト等の属性、XML で宣言された接続 | `setupUi`、`connectSlotsByName`、`on_<objectName>_<signal>` と実装の対応 |
| Signal／Slot | Qt メタオブジェクトのマクロ、`Q_PROPERTY`、`signals`／`slots` の宣言候補、`connect` の式・形式・条件 | 条件付きコンパイル、引数型、寿命、実行時の接続成立 |
| QML・リソース | `import`、`id`、`property`、`Connections`、ハンドラー等の記述、`qmldir`、`.qrc` の prefix／alias、C++ 側の `setContextProperty` や `qmlRegister*` | 動的 binding、JavaScript 評価、QML コンポーネントの実行時解決 |
| プラグイン・設定 | `Q_PLUGIN_METADATA` の IID と JSON 参照、`Q_DECLARE_INTERFACE`、`Q_INTERFACES`、`Q_IMPORT_PLUGIN`、`QPluginLoader`・`QLibrary`・登録関数や `QSettings` の使用候補 | IID を共有する実装の区別、所属、動的 Factory、有効化条件、読込と初期化の順序 |

根拠はスナップショットのルート相対パス、原本ハッシュ、文字コード、行範囲、原本バイト範囲で追跡できる。解析結果の `source_fact` はソースに現れる記述、`candidate` は接続・所属等の候補、`unresolved` は解決できない関係を表す。XML の根拠はファイル全体を指す場合がある。記述の存在と実行時の成立はレビューで照合する。

## 生成文書と検証

固定版 CodeWiki の `CLIDocumentationGenerator` が作業コピーから説明を生成する。`cpp-scan` はその Markdown を既定の日本語資料と組み合わせる。

| 文書 | 内容 |
| --- | --- |
| `overview.md` | 全体構成、文書リンク、入力一覧 |
| `plugins.md`、`screens.md` | プラグインの宣言・ローダー候補と、画面・操作の静的情報 |
| `processes.md`、`api.md` | 処理の起動契機、接続式、構成要素、API・プロパティ等 |
| `unknowns.md` | 欠落、解析範囲、構文エラー候補、未確認事項 |
| `wiki/*.md`、`qt/*.md` | CodeWiki の説明、ソースファイル別の Qt 補完 |

UTF-8、必須文書、成果物一覧・ハッシュ、内部リンクと見出し、ソースの根拠パスと行範囲を照合する。コードブロック内の記述は保持する。根拠の所在を確認できても、説明とソースの意味の一致、業務要件、実行時の成立は `unreviewed` とし、レビューで確認する。Mermaid の外部検証は無効。

CodeWiki のページ名は所有ファイル集合を基に安定化し、所有情報がない場合は元の相対パスを使う。旧ページ名と出力名の対応を生成 manifest に記録する。所有集合が変わると出力パスも変わり、旧資料が受渡し時の削除候補になる場合がある。

## 版と成果物

| 版 | ID の形式 | 主な成果物 |
| --- | --- | --- |
| 原本 | `snap-` ＋小文字 16 進数 64 桁 | `objects/` に内容ハッシュで原本を保管。`snapshots/<id>/` に `original/`、`utf8/`、`maps/`、`manifest.json` |
| 解析 | `analysis-` ＋小文字 16 進数 32 桁 | `analyses/<id>/` に `analysis.json`、`codewiki-raw.json`、`manifest.json` |
| 生成 | `gen-` ＋小文字 16 進数 32 桁 | `generations/<id>/` に `documents/`、`codewiki/`、`analysis.json`、`manifest.json`、`quality-report.json`、`usage.json`、`review.md` |
| 受渡し | 受渡し実行 ID | `handoff/current/` の Markdown と `state/handoffs/<run_id>.json` の取込結果 |

パスは `artifact_root` からの相対パス。原本版は入力元、対象、ハッシュ、収集・デコードの条件等から決まる。同じ原本版・解析条件または同じ解析版・生成条件に対しては、成功済みの成果物を照合して再利用する。生成条件にはモデル、エンドポイントのハッシュ、応答・リクエスト・深さの制限、実装の版を含む。`--force` は指定工程の版を新規作成し、旧版を保持する。コメント、画面、参考ファイルの変更も原本版の変更として扱う。

`state/state.json` と `state/runs/` に選択版と履歴を残す。工程全体が失敗した新しい解析版・生成版は、その工程の選択済みの版を置き換えない。部分完了の解析版・生成版は保存・選択できるが、成功済みキャッシュには登録されない。原本版の選択は解析の完了を待たずに更新されるので、必要な組合せは各 manifest で確認する。終了コードは `0` 成功、`1` エラー、`2` 部分完了、`130` 中断。

## 下書きへの受渡し

`ingest` は専用のナレッジ・収集元に対し、生成版とその原本・解析の対応、文書のハッシュ、入力元、既存スキーマと保管先を検証し、Markdown 一式を引き渡す。設定と実パスの検証は、受渡しフォルダの配置・中断復旧より先に行う。`storage_dir` と `report_dir` は C++ 入力ルート内および `handoff/` と親子・同一関係にある場所を拒否する。ファイル型 SQLite DB は `handoff/` の内側への配置を拒否する。

既定では部分完了の生成版を拒否する。`allow_partial_ingest: true` の場合、生成に含まれない旧 Markdown を保持し、`retained_paths` に記録する。元の `source_id`・`knowledge_id`・受渡しルートは固定する。原本ルート・収集範囲の変更や既存文書の削除候補は、完全版に対する `--accept-scope-change` を必要とする。削除候補は `status` の `latest.ingest.planned_removals` に記録する。

プロジェクト単位の排他を取り、`pending/`、`current/`、`previous/` と `state/handoff-journal.json` で配置を管理する。DB 取込が始まる前の中断は次回の取込で配置を復旧する。DB 取込開始後は同じ生成版の再取込で照合し、確定単位は 1 文書。取込結果には生成版・原本版、取込実行 ID、文書 ID、Markdown ハッシュ、選択抽出世代を記録する。

内容・変換条件が同一の文書は選択抽出世代と既存の公開状態を維持する。更新された文書は下書きの抽出世代を確認し、Embedding を実行して明示公開する。文書の版と検索公開の関係は[ファイル取込仕様書](../file-scan/仕様書.md)と[検索 API 仕様書](../file-search/仕様書.md)を参照。
